# Демон bbtunneld - документ решений

**Утверждён Мишей 2026-09-30 целиком (все 7 пунктов §15).** Ход работы - в конце, §16.

Этап 3 плана (`PLAN.md`). Здесь - как устроен root-демон и почему. Каждое решение: что выбрано, что
отброшено, от чего на телефоне оно зависит. Решения, которые ждут проверки на Passport, помечены
**[телефон]** и имеют запасной вариант, чтобы код не ждал телефона.

Что уже есть: движок `engine/` (WireGuard + AmneziaWG, sans-IO, интероп с ядром и amneziawg-go пройден),
образец цикла `engine/test/interop/wg_interop.c`, зонд `daemon/probe/tunprobe.c` (от root на телефоне
ещё не запускался: tun, адреса, маршруты и `SO_BINDTODEVICE` / `SO_SETFIB` не подтверждены).

## 0. Коротко

- Один C-процесс `bbtunneld`, один поток, один `poll`. Ядро переносимое, под ним платформенный слой:
  Linux (WSL, для разработки и тестов) и QNX (телефон).
- Профили и ключи хранит **демон** в каталоге только для root; приложение ключей обратно не получает.
- Приложение и headless-сервис говорят с демоном по **unix-сокету** в песочнице приложения, текстовым
  протоколом в духе UAPI WireGuard (`ключ=значение`, пустая строка - конец блока), со **событиями**
  вместо опроса.
- Полный туннель - маршруты `0/1` + `128/1` (и `::/1` + `8000::/1`) в FIB 0; свой UDP-сокет держим вне
  туннеля через FIB 15, запасной путь - host-маршрут к серверу **[телефон]**.
- DNS - `_CS_RESOLVE`, с возвратом и повтором после каждого вмешательства сетевого менеджера. Имена
  серверов демон разрешает **сам**, через DNS физической сети, мимо туннеля.
- Смена сети: слушаем routing-сокет и PPS, переустанавливаем маршруты и DNS, пересоздаём сокет,
  заново разрешаем имя, сразу начинаем рукопожатие.
- Kill switch через pf - **не в первой версии**; в v1 «без утечек на время переподключения» за счёт
  маршрутов. pf - отдельный шаг после чтения системных правил.
- Несколько туннелей сразу - в архитектуре с первого дня (до 4, по числу `/dev/tunN`); маршрут по
  умолчанию - не больше чем у одного.
- Порядок: ядро + Linux-бэкенд, всё проверено в WSL в сетевых namespace против ядерного WireGuard и
  amneziawg-go; потом QNX-бэкенд на телефоне.

## 1. Процесс и запуск

**Решение.** `bbtunneld` - C (gnu99, как движок), без Qt и без C++ рантайма; движок линкуется исходниками.
Один поток, цикл на `poll`: сокет управления и его клиенты, по tun и UDP-сокету на туннель, routing-сокет,
PPS, таймер. Таймаут `poll` - минимум из `wg_device_next_deadline` всех туннелей и своих таймеров
(debounce смены сети, повтор разрешения имён, статистика). Время - `CLOCK_MONOTONIC` в нс.

Бинарник едет в `.bar` ассетом `Qnx/Elf` - это единственное место, откуда BB10 вообще исполняет наш код
(PLAN §2).

**Кто запускает - открытый вопрос, он за Мишей (PLAN §2).** Документ от способа не зависит; демону нужно
одно: его запускают от root при загрузке и **перезапускают, если он вышел** (простой цикл «запустить,
подождать 2 с, снова»). На этом держится обновление (п. 12) и восстановление после падения.

Отброшено: демон на Qt (лишний рантайм в root-процессе, не нужен); несколько потоков (движок
однопоточный, а весь ввод-вывод помещается в `poll`).

## 2. Где живут профили и ключи

**Решение: у демона.** Каталог `state/` только для root (`0700`), по файлу на профиль:

- `<id>.conf` - текст ровно как импортирован (источник правды; при подключении разбирается заново
  `wg_conf_parse`, поэтому ни AmneziaWG-параметры, ни будущие ключи не требуют своей сериализации, а
  экспорт позже - просто отдать файл);
- `<id>.meta` - `ключ=значение`: имя, тип, дата импорта, автоподключение, порядок в списке, служебное
  (метки рукопожатия, п. 9).

Запись атомарная: временный файл, `fsync`, `rename`. `id` - 8 случайных hex-символов.

Где каталог - **[телефон]**:
- предлагаю внутри песочницы приложения: `/accounts/1000/appdata/<пакет>/data/daemon/` (root, `0700`).
  Удаление приложения стирает и ключи - так и должно быть. Путь демон знает сам: он запущен из
  `/apps/<пакет>/native/`, а имя каталога песочницы то же. Проверить: удаляет ли деинсталляция
  каталог, принадлежащий root, и не ломает ли он бэкап/восстановление приложения;
- запасной - `/var/bbtunnel/` (переживёт удаление приложения - минус).

Отброшено: профили в SQLite приложения, ключ передаётся демону при подключении. Тогда автоподключение при
загрузке зависит от того, поднялся ли headless-сервис, приватные ключи лежат там, откуда их читает любой
код приложения, а демон становится «тупым исполнителем» без своей памяти. Приложению ключ не нужен:
импорт отдаёт текст, дальше UI видит имя, публичный ключ, адреса и сервер.

## 3. Протокол приложение <-> демон

**Транспорт.** Unix stream-сокет `data/daemon.sock` в песочнице приложения. Демон создаёт его и отдаёт
uid приложения, права `0600` - дотянуться могут только наше приложение, наш headless-сервис (у них одна
песочница и один uid) и root. Если в QNX есть `getpeereid` / `LOCAL_CREDS` - дополнительно проверяем uid
собеседника **[телефон, по заголовкам NDK]**. Длина пути укладывается в `sun_path` (104 байта) - проверить
на реальном имени пакета. `QLocalSocket` в приложении с таким сокетом работает (Beacon в BBTelega).

**Формат - как UAPI WireGuard:** блок строк `ключ=значение`, конец блока - пустая строка. Первая строка
блока говорит, что это (*уточнено на шаге 2:* плюс `item=<вид>` - элементы списка, которые идут перед
ответом `profile.list` и `status` с тем же `id`, по блоку на профиль или туннель - так группировка не
держится на порядке повторяющихся ключей):

```
-> cmd=tunnel.up          <- reply=tunnel.up          <- event=tunnel
   id=7                      id=7                        profile=3fa81c02
   profile=3fa81c02          errno=0                     state=connecting
                                                         reason=
```

`id=` запроса возвращается в ответе, так что события и ответы идут по одному соединению вперемешку.
`errno=0` - успех; иначе `errno=<код>` + `error=<текст>` (и `line=` для ошибок `.conf`). Незнакомые ключи
игнорируются обеими сторонами - так старое приложение переживает новый демон и наоборот. Имена
статистики берём из UAPI (`rx_bytes`, `tx_bytes`, `last_handshake_time_sec`), чтобы не выдумывать.

Отброшено: JSON (в демоне нужен парсер, а в Qt 4.8 нет `QJson`; `ключ=значение` - десяток строк с обеих
сторон); ровно UAPI WireGuard (он про одно устройство, а у нас профили, маршруты, DNS, несколько туннелей -
пришлось бы расширять всё равно); общая SQLite как в Syno (root-процесс, пишущий в базу приложения, и опрос
вместо событий).

Причины состояния у Tailscale: `control` (нет связи с сервером управления; `detail` - почему), `relay`
(домашний DERP не готов), `approval` (узел в сети, ждёт одобрения админа), `login` (ключ авторизации не
принят, вход отозван), `expired` (вход истёк) и `removed` (узла больше нет в сети: удалён админом или
временный ушёл сам) - три последних в `error`, до нового входа; `browser` (демон 0.3.0) - вход по ссылке
ждёт, пока по ней войдут на другом устройстве (`connecting`, ссылка - `auth_url`).

**События:** `event=tunnel` (смена состояния), `event=stats`, `event=network` (сменилась сеть -
для диагностики), `event=profile` (список изменился - второй клиент увидит правку первого).

**Состояния туннеля:** `down`, `connecting` (разрешаем имя / первое рукопожатие), `up` (рукопожатие
моложе 180 с), `reconnecting` (сеть сменилась или рукопожатие устарело, маршруты на месте), `error`
+ `reason`: `resolve` (имя не разрешается), `no_network`, `handshake` (сервер молчит: неверный ключ, не
тот протокол или блокировка - UI подскажет попробовать AmneziaWG), `tun`, `route`, `dns`.

Парсер протокола - отдельный файл без ввода-вывода; фаззим как движок (root-процесс разбирает чужой ввод).
Лимиты: блок до 256 КБ (длинный `.conf` раздельного туннеля), до 8 клиентов.

## 4. Туннель изнутри

Каждый поднятый профиль - `tunnel`: `wg_device` + свободный `/dev/tunN` (0-3) + свой UDP-сокет +
применённые маршруты и DNS + память движка (пиры, кольца ожидания, узлы AllowedIPs, `wg_awg`) одним
`malloc` по размерам из `.conf`. Upcall-ы как в `wg_interop`: `send` -> `sendto`, `deliver` -> `write` в
tun с 4-байтным заголовком семейства (`AF_INET6` = 24 на QNX, 10 на Linux - это знает бэкенд);
вызывать устройство из upcall-а нельзя - отложенное уходит после возврата.

- **MTU:** из `.conf`, иначе 1420; для AmneziaWG минус префикс данных S4. Подсказка в UI: на LTE и при
  проблемах - 1280.
- **ListenPort:** из `.conf`, иначе любой свободный.
- **IPv6:** если у профиля есть v6-адрес - как положено; если AllowedIPs содержит `::/0`, а v6-адреса нет -
  v6-маршруты всё равно в tun (пакеты там умирают), чтобы v6 не утёк мимо туннеля, как в wg-quick.
  Работает ли v6 через tun на QNX - **[телефон]** (зонд это проверяет).
- **`WG_DROP_NO_ROUTE`** - просто отбрасываем; ICMP unreachable - позже, если понадобится.

## 5. Маршруты и свой трафик мимо туннеля

**Маршруты.** Каждый префикс AllowedIPs -> маршрут на `tunN` в FIB 0 (личный периметр); `/0`
превращается в пару `/1` (так маршрут по умолчанию сетевого менеджера не трогаем и не спорим с ним - наш
просто точнее). Ссылочные маршруты локальной сети (`192.168.1.0/24` и USB `169.254.0.0/30`) точнее `/1`
и остаются мимо туннеля - SSH по USB не рвётся.

**Свой UDP-сокет не должен уйти в туннель** (сервер попадает в `0/1`). Варианты по порядку:

1. **FIB 15** (`SO_SETFIB 15` на сокете): у FIB 15 свой `default` через физическую сеть, его ведёт система,
   наши маршруты живут только в FIB 0 - петли нет при любой смене сети, и ничего не надо
   переставлять. Нужно подтвердить: принимается ли опция, и следует ли FIB 15 за переходом на LTE
   **[телефон]**. Возможно, проще - демону состоять в группе `all_fib` (gid 765): по `mfib_gid_map` все его
   сокеты сами попадут в FIB 15; тогда вопрос, пишут ли его сообщения routing-сокета в FIB 0.
2. **`SO_BINDTODEVICE`** на физический интерфейс - если зонд покажет, что он переигрывает маршруты.
   Минус: при смене Wi-Fi <-> LTE сокет пересоздаётся на другой интерфейс.
3. **Host-маршрут к серверу** через текущий физический шлюз (что делает wg-quick на macOS/BSD). Работает
   везде, но шлюз меняется при каждом переходе, маршрут надо переставлять, а сетевой менеджер может его
   стереть.

Код один: бэкенд даёт «сделай сокет, который ходит мимо туннеля»; способ выбирается по итогам зонда.
В Linux-бэкенде - `SO_BINDTODEVICE` на интерфейс маршрута по умолчанию (вариант 2): привязанный сокет
видит только маршруты через свой интерфейс, `/1` туннеля его не ловят. *Уточнено на шаге 2:* так
проще, чем `SO_MARK` + своя таблица, и заодно проверяет на деле вариант 2 со сменой интерфейса.

*Уточнено на шаге 3:* вариант 3 сделан - `--egress hostroute`; на QNX в `auto` он включается сам, когда
FIB 15 нет, и тогда `SO_BINDTODEVICE` идёт вторым слоем (с host-маршрутом они не спорят). Ему нужен
адрес сервера, поэтому часть работы - в ядре (`bt_tunnel.c`):
- ядро собирает, куда ходят наши сокеты: конечные точки пиров и DNS-серверы, пока ищется имя; бэкенду
  отдаёт те, что ловят маршруты туннелей (поиск по дереву AllowedIPs движка) - раздельному туннелю без
  полного маршрут к серверу не нужен;
- набор пересчитывается при подъёме и опускании туннеля, после поиска имени (до рукопожатия), при
  смене сети (до новых рукопожатий) и перед `sendto` на адрес не из набора (пир переехал): маршрут
  всегда встаёт раньше пакета;
- бэкенд ставит host-маршрут через шлюз физического маршрута по умолчанию с меткой «наш» (QNX -
  `RTF_PROTO2`, Linux - `proto 126`), переставляет при смене шлюза, после события сети проверяет, не
  стёр ли его сетевой менеджер. Адрес в подсети интерфейса пропускается: его и так уводит маршрут
  подсети, а через шлюз он только отскочил бы от роутера;
- после падения: host-маршруты записаны в журнал применённого (`bypass=`), удаляются только помеченные
  как наши.

Не закрыто: сервер в собственной подсети телефона, когда AllowedIPs туннеля точнее этой подсети
(туннель в свою же локальную сеть, находясь в ней) - маршрут туннеля перебьёт маршрут подсети, а
host-маршрута нет. В Linux-бэкенде тот же режим, e2e гоняется в обоих (`run.sh hostroute`).

Раздельный туннель на тысячи префиксов - тысячи маршрутов в io-pkt; выдержит ли он и сколько это
ставится - **[телефон]**, на Linux - проверим сразу.

## 6. DNS

- Профиль с `DNS=`: при подъёме запоминаем текущее `_CS_RESOLVE` (в файл - на случай падения, п. 11) и
  ставим свои серверы и домены поиска; при опускании - возвращаем **то, что сейчас считает правильным
  сетевой менеджер** (из PPS `status_public`), а не сохранённое: сеть за это время могла смениться.
- Сетевой менеджер переписывает DNS при каждой смене сети - после его события ставим свой снова (п. 7).
  Окно в доли секунды, пока в силе системный, остаётся; закрыть его может только pf (п. 8).
- Профиль без `DNS=` при полном туннеле: DNS остаётся системным (часто роутер в локальной сети - мимо
  туннеля). UI предупредит.
- Несколько туннелей: DNS ставит туннель с маршрутом по умолчанию, иначе последний поднятый.
- Видят ли новый DNS уже запущенные приложения и Android-рантайм - **[телефон]** (PLAN §4).

**Имена серверов (`Endpoint = vpn.example.com:51820`) демон разрешает сам**: маленький неблокирующий
клиент DNS (A/AAAA, ~300 строк) в том же `poll`, запросы идут через сокет мимо туннеля к серверам
**физической** сети (из PPS). Иначе ловушка: после установки нашего DNS `getaddrinfo` пошёл бы к
DNS внутри туннеля, который как раз не работает, - и при смене адреса сервера туннель не поднялся бы
никогда; к тому же `getaddrinfo` блокирует весь цикл на секунды. Последний удачный адрес храним в `.meta`
и используем, пока новый не получен. Отброшено: `getaddrinfo` в отдельном потоке (не выбрать сервер
DNS).

## 7. Смена сети, сон

**Как узнаём:** routing-сокет (`PF_ROUTE`: добавление/удаление маршрута по умолчанию, адреса,
состояние интерфейсов - обычный BSD, проверен зондом на `RTM_GET`) + PPS
`/pps/services/networking/status_public` (`default_interface`, `nameservers`) в режиме ожидания изменений.
BPS `netstatus` не берём: это API приложений, работает ли он в процессе вне лаунчера - неизвестно, а PPS
- обычный файл в `poll`.

**Что делаем** (с задержкой ~500 мс, чтобы пачка событий менеджера схлопнулась в одно):
1. переставить свои маршруты, если их стёрли; снова свой DNS;
2. пересоздать UDP-сокет (новый исходный адрес - то же, что Linux делает сбросом исходного адреса);
3. заново разрешить имя сервера;
4. `wg_peer_initiate` - не ждать таймеров: сервер увидит нас с нового адреса сразу (роуминг в движке
   уже есть). Состояние - `reconnecting`, пока рукопожатие не пройдёт.
   *Уточнено 2026-09-30 (тест клиента, APP §15):* рукопожатие, сделанное **до** смены сети, не в счёт.
   Раньше оно, моложе 180 с, тут же возвращало `up`, и сервер, потерянный при переезде, до трёх минут
   выглядел подключённым. Теперь `reconnecting` держится до рукопожатия после смены **или** до
   подлинного пакета от сервера после неё: сессия продолжается с нового адреса и без рукопожатия, а
   новый `wg_peer_initiate` движок пропускает, если прошлый был меньше `REKEY_TIMEOUT` назад. Молчит
   сервер - через 15 с причина `handshake`, как у `connecting`.

Нет сети вовсе - `no_network`, маршруты остаются (трафик не утекает, он просто стоит), таймеры движка
дальше не крутим впустую: при пропаже default отключаем keepalive до возврата сети.

**Сон.** В standby сеть на BB10 остаётся (исследование, Q4); держит NAT-маппинг `PersistentKeepalive`
из профиля. Для профилей без него UI предложит 25 с. Идёт ли `CLOCK_MONOTONIC` во сне и как часто
просыпается телефон с keepalive 25 с - **[телефон]**, замерить расход батареи.

## 8. Kill switch

**Решение для v1: без pf.** Пока туннель поднят или переподключается, маршруты `/1` остаются, и трафик
идёт в tun, а не мимо (пусть и в никуда). Чисто опускаясь, убираем всё. Этого нет при падении демона и в
окне смены DNS - это закрывает только фильтр.

**pf - отдельным шагом после v1:** на телефоне `lsm-pf` уже загружен и, возможно, у системы свои правила
(корпоративный периметр). Сначала прочитать их (`pfctl -s rules`, `-s Anchors`, только чтение), потом решить:
свой anchor «пропускать только tun, наш сокет и локальную сеть» или ничего. Ломать системные правила
нельзя - это может отрезать телефон от сети. Kill switch по умолчанию - **выключен**, включается в
настройках.

## 9. Метка времени рукопожатия между перезапусками

Движок держит метку initiation строго растущей (`wg_noise_remote.sent_timestamp`), но только в памяти.
После перезапуска демона с часами, ушедшими назад, сервер отвергал бы нас, пока часы не догонят.
**Решение:** храним в `.meta` профиля «потолок» - все отправленные метки ниже него; после перезапуска
первая метка берётся от потолка, что бы ни показывали часы; потолок переписывается, только когда метки
его догоняют.

*Уточнено на шаге 2:* запас - **10 минут**, а не час. Метка после перезапуска начинается от
потолка, то есть впереди часов, и каждый перезапуск сдвигает её вперёд на запас: при часе частые
перезапуски увели бы метки на часы вперёд (а после переустановки с потерей состояния сервер ждал бы,
пока часы их догонят). В пределах одного запуска демона последняя отправленная метка профиля
помнится точно, и повторный подъём туннеля потолок не трогает. Запись на диск - раз в ~10 минут
рукопожатий. Проверено в e2e: часы на час назад - сервер принимает; контроль без потолка и на два
часа назад - сервер отвергает.

*Уточнено 2026-09-30 (тест клиента, APP §15):* потолка профиля мало - один ключ бывает в двух профилях
(импортирован дважды, удалён и импортирован заново), а сервер помнит самую новую метку ключа. После
перезапусков старый профиль ушёл вперёд часов, новый начинал по часам, и сервер его отвергал, пока часы не
догонят. Теперь у демона есть общий **пол** - `ts_floor` в `settings`, наибольший потолок любого профиля,
удалённого тоже. Первая метка профиля берётся не ниже самой новой метки любого профиля в этом запуске
(поднятых и опущенных), а после перезапуска - не ниже пола. Дрейф тот же, что у потолка: запас на каждый
перезапуск. e2e: ключ удалённого профиля в новом профиле поднимается сразу; контроль шага 10 обнуляет и
пол.

## 10. Несколько туннелей

Архитектура - N туннелей в одном цикле с первого дня (дёшево: массив структур). Правила:
- не больше 4 (по `/dev/tun0-3`);
- маршрут по умолчанию - только у одного; второй профиль с `0/0` при поднятом первом - ошибка с
  понятным текстом (или предложение переключиться);
- раздельные туннели живут рядом с полным: их префиксы точнее `/1`.

Ради этого всё и затевалось: Tailscale (`100.64.0.0/10` и MagicDNS) рядом с полным AmneziaWG. UI v1 может
показывать один активный, протокол уже про несколько.

Всегда включённых мест два: WireGuard или AmneziaWG (`always_on`) и Tailscale (`always_on_tailscale`), как и в
ручном режиме. При старте демон поднимает сначала первый: связи Tailscale тогда идут внутри полного туннеля. Настройка
версий до 1.1.0 с профилем Tailscale в `always_on` при старте переезжает на его место (`always_on_settle` в `main.c`).

## 10a. Значок VPN в статус-баре

Штатный ключ рисует навигатор по PPS-объекту `/pps/system/navigator/status/vpn`. Туда же пишет системный менеджер
VPN для своих подключений (`vpn_pps`, функция `vpn_icon_state_update`), и наша запись такая же:
`[n]dat:json:{"vpn":{"state":"connected"}}`. Навигатор понимает `off`, `on`, `connected`, остальное считает `off`.
Найдено в коде прошивки 10.3.3.3216 (`/usr/sbin/vpn_pps`, `/usr/hmi/sys.navigator/navigator`). На телефоне ключ
горит (2026-11-09, сборка 44, проверил Миша).

Демон показывает туннели в целом (`status_icon_update` в `bt_tunnel.c`, запись - `bt_status_icon` в бэкенде):
- `connected` - хотя бы один туннель `up`;
- `on` - ни одного `up`, но есть `reconnecting`: при смене сети ключ не пропадает;
- `off` - всё остальное, первое подключение тоже.

Правила:
- пишем только при смене значения: навигатор на каждую запись перерисовывается;
- `off` при старте демона: упавший мог оставить ключ гореть. `[n]` значит, что перезагрузку значение не переживает;
- объект не создаём (нет `O_CREAT`): он принадлежит `vpn_pps`, созданный нами был бы root-овым и закрытым для него;
- каталог закрыт (`root:navstatus`), приложение и сервис туда не попадут - только демон;
- Настройки > VPN читают другой объект (`/pps/services/vpn/status`) и о наших туннелях не знают;
- рядом с системным IKEv2 ключ покажет то, что записано последним: `vpn_pps` пишет при своих событиях, мы - при своих.

## 11. Журнал, падения, восстановление

- **Журнал:** `data/logs/daemon.txt` в песочнице приложения (владелец - uid приложения, чтобы его можно
  было открыть и поделиться; `.txt`, потому что штатный просмотрщик `.log` не открывает), два файла по
  256 КБ по кругу, уровни `E W I D`. Никогда не пишем приватные ключи, PSK и `HeaderProtectionKey`.
  `log.tail` отдаёт хвост по сокету.
- **Журнал применённого:** перед каждым изменением системы (маршрут, DNS, tun) - строчка в
  `state/applied`. При старте демон читает его и убирает хвосты после падения: маршруты на `tunN`,
  чужой DNS. Иначе упавший демон оставит телефон с DNS `10.x`, который никуда не ведёт.
  *Уточнено на шаге 2:* в журнале не маршруты по одному (у раздельного туннеля их тысячи), а имена
  tun-устройств и системный DNS на момент подмены; маршруты устройства после падения убирает бэкенд
  (`bt_routes_flush`; на Linux они умирают вместе с устройством). Журнала нет - всё чисто.
  *Уточнено на шаге 3:* ещё строки `bypass=<адрес>` - host-маршруты к серверам (§5, вариант 3); они идут
  через физический интерфейс, устройство их с собой не унесёт, поэтому при старте удаляются по одному -
  и только помеченные как наши.
- **Один демон на каталог состояния:** блокировка `fcntl` на `state/lock`, второй экземпляр выходит
  сразу, ничего не тронув. Ядро снимает её вместе с процессом, как бы тот ни кончился.
- **SIGTERM** - всё опустить чисто и выйти.

## 12. Обновление приложения

Переустановка `.bar` подменяет бинарник, но работающий демон остаётся старым. Приложение на `hello`
видит, что версия протокола или демона старше своей, и шлёт `daemon.restart`; демон опускает туннели,
выходит, внешний цикл запускает новый. Always-on профиль поднимается снова сам. Остаётся ли каталог
пакета тем же после обновления (путь к бинарнику для перезапуска) - **[телефон]**.

*Изменено 2026-10-15 (телефон):* каталог пакета после обновления тот же. Но копия демона, сделанная после
загрузки, не запускается (`Operation not permitted`), только та, что лежала в RUN при загрузке. Поэтому
обновление - с перезагрузкой (решение Миши): цикл копирует новый пакет сразу, при работающем старом
демоне (наблюдатель раз в `WATCH` с), приложение `daemon.restart` не шлёт, а говорит о перезагрузке
(APP §9). `BT_VERSION` поднимается при каждой правке демона.

*Уточнено 2026-10-14 (цикл запуска `daemon/boot/bbtunneld-boot.sh`):* обновление не трогает цикл. Он
ищет пакет по шаблону `/apps/doctorrokter.BBTunnel.*` перед каждым стартом, так что новый бинарник
подхватывается сам (с 2026-10-15 - копируется в `/accounts/devuser/rootdata/bbtunneld-boot/`, если его
`cksum` изменился, и запускается оттуда; PLAN §0). Если система при установке сама убьёт демон, цикл запустит новый через 2 с. Цикл лежит
вне пакета и меняется руками; новая версия начинает работать со следующей загрузки, потому что из
root-SSH демон не стартует. Запускаемый цикл в `.bar` не кладём: ошибка в нём, приехавшая с обновлением,
попала бы в загрузку, а после удаления приложения в автозапуске осталась бы ссылка в никуда. *С 2026-10-23*
пакет везёт его копию только для передачи (`native/bbtunneld-boot.sh`): гид «Как начать» (APP §17) кладёт её в
общую `misc/`, человек от root копирует её в папку, куда пишет только root, и автозапуск запускает ту копию -
обновление приложения её не трогает, как и раньше. Папку для копий демона (RUN) root-настройка может задать
единственным аргументом: `sh bbtunneld-boot.sh /папка` - RUN становится `/папка/bbtunneld-boot` (0700),
запасной журнал - `/папка/bbtunneld-boot.txt`; без аргумента - прежние пути. Берётся только полный путь
существующей папки, без `..` и не в общей памяти (туда пишут приложения, а root запустил бы их файл);
иначе запуск кончается строкой «exit: the folder for the daemon's copies (the argument) is not usable - ...».
Тест цикла - 243 проверки (раздел 23 - аргумент и отказы). Отсюда правила для
каждой новой версии демона:
- `--state --socket --log --owner` принимаются всегда, с тем же смыслом. Новые настройки идут через
  приложение в `settings`, а не в командную строку - иначе пришлось бы менять цикл на телефоне;
- новый демон читает состояние старого (профили, `settings`, профиль Tailscale, журнал применённого);
  смена формата - переводом при старте, не отказом;
- старое приложение с новым демоном работает (незнакомые ключи пропускаются, APP §9).

*Изменено 2026-11-08 (root v4, как в GPS Boost; решение Миши):* запрет «цикл не приезжает с обновлением» теперь
только для ручной установки (v2). Headless-сервис при каждом своём старте зовёт `/base/bin/__root`, затем
`/bin/__root` и передаёт ему `/bin/ksh -s install '<файл>' < '<файл>'` с `native/bbtunneld-boot.sh` пакета
(`client/service/RootAutostart`, до 16 попыток раз в минуту, 60 с на попытку, итог - последняя строка
`result=ok|same|failed`; обёртки нет - ничего не делает, ручная установка работает как раньше). Скрипт кладёт себя
целиком в `/var/addons/tunnel/init/start.sh` (решение Миши 2026-11-09: второго файла нет, система запускает сам
скрипт), только при отличии, через `.new` и `mv`; ошибка из обновления
может попасть в загрузку, но поздний старт (до ~15 минут) оставляет время удалить приложение или включить
`tunnel-off`. Там же сразу лежат копии демона (`bbtunneld-boot/`, 0700), так что первая же перезагрузка запускает
его. Запущенный под любым именем, кроме `*boot.sh`, скрипт считает, что его запустила система, какие бы аргументы
ни пришли. Следующий `install` переносит запасной журнал в `misc/bbtunneld-boot.txt`. После загрузки из хука скрипт просит навигатор поднять сервис
(`bb.action.START`, раз в 30 с, до 15 минут): системный `STARTED` приходит раньше root. Приложение удалено - хук
удаляет всю папку. Две загрузки сразу (ручная строка и хук) - второй цикл выходит, увидев первый по pid и `pidin`.
Тест цикла - раздел 24. **[телефон v4, сборка 36, 2026-11-08]:** хук сработал при загрузке, цикл и служба приложения поднялись; старт демона кончился статусом 1 (строка в `misc/bbtunneld-boot.txt`). **[телефон v4, сборка 39, 2026-11-09]:** служба заработала (проверил Миша). С этой сборки скрипт сразу после открытия журнала, до запуска демона, вызывает `/proc/boot/pathtrust` для `$ADDON`, `$RUN`, `$RUN/bbtunneld` и `$RUN/btctl` (добавил Миша); итог каждого вызова - строка `pathtrust <путь>: status N` в журнале.

**[телефон], при первом обновлении с работающим демоном:** имя каталога пакета то же; установка проходит,
пока старый бинарник работает (если нет - выключатель `misc/tunnel-off` и «Перезапустить сервис», установить,
выключатель убрать); `data/daemon` пережил обновление и всё ещё root `0700`; в журнале демона -
`stopping for a restart` и `starting` с новой версией.

## 13. Роль headless-сервиса (этап 4, здесь - контракт)

Сервис - клиент демона, как приложение: при загрузке подписывается `watch` без статистики, показывает
уведомления («подключено / связь потеряна», по настройке), замечает, что демон не отвечает, и говорит
об этом (перезапустить его он не может - он не root). Always-on - забота демона, сервис для этого не нужен.

## 14. Раскладка кода и порядок работы

```
daemon/
  src/main.c        аргументы, сигналы, старт: восстановление, always-on
  src/loop.{h,c}    poll, таймеры, раздача событий
  src/tunnel.{h,c}  туннель: устройство + tun + сокет + маршруты + DNS, состояния
  src/store.{h,c}   профили и .meta на диске, атомарная запись
  src/ctl.{h,c}     сокет управления, клиенты, подписки
  src/proto.{h,c}   разбор и сборка блоков - без ввода-вывода, под фаззер
  src/resolve.{h,c} неблокирующий клиент DNS
  src/log.{h,c}
  src/plat.h        бэкенд: tun, адреса, MTU, маршруты, DNS, сокет мимо туннеля, события сети
  src/plat_linux.c  WSL
  src/plat_qnx.c    телефон
  test/             proto, store, resolve, фаззер; e2e в netns
  build.sh          host | cross | all, как у движка
  probe/            зонд - как есть
```

**Шаги:**
1. `proto`, `store`, `log`, `resolve` + тесты и фаззер (без сети).
2. `loop`, `tunnel`, `ctl` + Linux-бэкенд. **Проверка в WSL целиком:** два сетевых namespace - «телефон»
   (наш демон, настоящий tun) и «сервер» (ядерный WireGuard, затем amneziawg-go) через veth; маленький
   клиент протокола вместо приложения. Сценарии: импорт с ошибкой в строке, подъём, ping и TCP через
   туннель, полный туннель с сокетом мимо него, смена «сети» (перевесить адрес / маршрут по умолчанию),
   имя сервера меняет адрес, два туннеля сразу, `kill -9` и восстановление, `daemon.restart`. Хост WSL при
   этом не трогается.
3. QNX-бэкенд, кросс-сборка, в `.bar`. Проверяет Миша на Passport - когда будет решён запуск от root;
   зонд `tunprobe tun --routes` - первым делом, он отвечает на половину **[телефон]** выше.

## 15. Что нужно от тебя

Утвердить или поправить:
1. Профили и ключи - у демона, в root-каталоге внутри песочницы (п. 2).
2. Протокол `ключ=значение` по unix-сокету в песочнице, с событиями (п. 3).
3. Свой трафик мимо туннеля - FIB 15, запасные пути по результатам зонда (п. 5).
4. Свой клиент DNS для имён серверов (п. 6).
5. Kill switch - не в v1, выключен по умолчанию, pf только после чтения системных правил (п. 8).
6. Несколько туннелей в архитектуре сразу, UI v1 - один (п. 10).
7. Порядок: WSL с netns до телефона (п. 14).

И от телефона, когда появится запуск от root: `tunprobe tun --routes` и `tunprobe dns` - это закрывает
tun, v6, `SO_SETFIB` / `SO_BINDTODEVICE` и запись `_CS_RESOLVE`.
