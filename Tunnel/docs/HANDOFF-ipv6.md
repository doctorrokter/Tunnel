# HANDOFF: IPv6-адрес на tun на телефоне (2026-10-15)

Одна задача: профиль WireGuard с IPv6-адресом должен подниматься на телефоне. Сейчас демон падает на
назначении IPv6-адреса интерфейсу tun. Всё остальное по туннелю работает (ниже). Разбора причины здесь нет:
начни с кода и заголовков SDK, указанных ниже.

## Симптом

Приложение, страница профиля: «Ошибка. Не удалось поднять туннель.
address 2606:4700:110:800c:4031:d028:ff5:8e1a/128: Invalid argument».

Журнал демона (`data/logs/daemon.txt`, уровень INFO; строки `BT_D` в нём не видны):

```
2026-10-15 16:04:39.367 I profile a74f0824 imported (wireguard)
2026-10-15 16:04:41.157 I tunnel a74f0824: error (tun: address 2606:4700:110:800c:4031:d028:ff5:8e1a/128: Invalid argument)
```

Тот же конфиг без IPv6 работает:

```
2026-10-15 16:16:32.401 I profile 1f4f54d6 imported (wireguard)
2026-10-15 16:16:33.619 I tunnel 1f4f54d6: tun1, mtu 1280, 1 peer(s), 1 prefix(es)
2026-10-15 16:16:33.637 I egress IPv4: FIB 15 + bound to bcm0
2026-10-15 16:16:33.647 I tunnel 1f4f54d6: IPv4 out via bcm0
2026-10-15 16:16:33.672 I tunnel 1f4f54d6: connecting
2026-10-15 16:16:33.676 I DNS: 1f4f54d6's servers
2026-10-15 16:16:33.752 I tunnel 1f4f54d6: engage.cloudflareclient.com is 162.159.192.1
2026-10-15 16:16:34.408 I tunnel 1f4f54d6: up
```

В браузере телефона `cloudflare.com/cdn-cgi/trace` показывает `warp=on`. Второй профиль получил `tun1`, а не
`tun0`: после ошибки первого туннеля `tun0` остался занят или не освободился. Это тоже стоит проверить.

## Сделано 2026-10-15: диагностическая сборка (buildId 16)

**Главный подозреваемый - `IN6_IFF_NODAD`** (на телефоне не подтверждено). В KAME, как в NetBSD 5
(`in6_control`, ветка `SIOCAIFADDR_IN6`), флаги `DUPLICATED`, `DETACHED`, `NODAD` и `AUTOCONF` считаются
«только для чтения», и на любой из них ядро отвечает `EINVAL` ещё до проверки адреса. io-pkt - NetBSD того же
времени: в `net/if_tun.h` SDK `simple_lock`, в `in6_var.h` прототипы через `__P`. Linux свой `IFA_F_NODAD`
принимает, поэтому в WSL ошибки не было. Остальное в запросе в порядке: сокет `AF_INET6`, `sin6_len` у адреса
и маски, сроки бесконечные, без дальнего конца.

Что изменено (только журнал и перебор, без нового способа включить отладку; аргументы демона те же):
- `bt_if_addr` (`bt_plat_qnx.c`, `addr6_try`) пробует по очереди и останавливается на первой удачной:
  с `NODAD` (как было) -> без `NODAD` -> без `NODAD`, дальний конец = свой адрес, `/128` -> после `IFF_UP` ->
  `/128`, если префикс был другой. Каждая попытка - строка INFO:
  `tun0: IPv6 2606:.../128 with NODAD: Invalid argument`, затем `... without NODAD: ok`.
- Без `NODAD` адрес проходит DAD: около секунды он «tentative», и IPv6 в первую секунду может не ходить.
  Запрос DAD (NS на `ff02::1:ff..`) уходит в туннель к серверу и там пропадает, вреда нет.
- **`tun1` вместо `tun0`.** У нас в учёте юнит освобождается верно: `fail` -> `release` -> `bt_tun_close`
  (`tun_used = 0`, `SIOCIFDESTROY`). Значит, `tun0` не отдала система (или он был занят ещё до первого
  профиля), и по коду не понять почему. Теперь в журнале: при открытии
  `tun1 taken, refused before it: tun0: <ошибка>, the interface exists | no interface`, при закрытии
  `tun0: closed, the interface destroyed` или `tun0: closed; SIOCIFDESTROY: <ошибка>, ...`.
- Маршрут, который не встал, пишется со своим префиксом: `tunnel <id>: route ::/0 did not go in: <ошибка>`
  (было одной строкой без префикса). IPv6-маршруты на телефоне ещё не ставились ни разу.

**Проверка на телефоне (Миша):**
1. Поставить `BBTunnel_1_0_0_16.bar`. Версия демона та же (`0.1.0`), поэтому приложение само его **не**
   перезапустит: Диагностика -> «Перезапустить службу». Новый демон узнаётся по строкам `IPv6 ...` в журнале.
2. Профиль `wgcf-profile.conf` как есть (с IPv6): включить. Потом браузер: `cloudflare.com/cdn-cgi/trace`
   (`warp=on`) и `http://[2606:4700:4700::1111]/cdn-cgi/trace` (`ip=` - IPv6-адрес).
3. Выключить, включить снова (тот же профиль), выключить.
4. Диагностика -> «Отправить журналы».

**Что в журнале решает дело:** какая строка `IPv6 ...: ok` первая (если `without NODAD` - причина
подтверждена, перебор сводится к одной попытке без `NODAD`); какие `tunN` берутся при каждом включении и что
пишет закрытие; строки `route ... did not go in` и `egress IPv6`. После разбора журнала строки перебора и
закрытия tun опускаются с INFO обратно, оставляем только рабочий вариант.

## Первый заход со сборкой 16 (2026-10-15 22:09-22:32): до IPv6 не дошло

- **22:09 - ещё старый демон.** Сборка 16 стоит с 17:25, но работал демон, запущенный в 15:53: версия
  та же (`0.1.0`), и приложение его не перезапустило (APP §9). В журнале демона нет строк перебора.
- **22:16 «Перезапустить службу» сработало** (`restart asked for`, демон вышел с кодом 0). Цикл скопировал
  новый `bbtunneld` в RUN, и каждый запуск копии - `Operation not permitted`, служба не работает. После
  перезагрузки в 22:30 то же самое.
- **Копия, сделанная после загрузки, не запускается; лежавшая в RUN при загрузке - запускается.** Копия
  от 15:15:54: в 15:16 и 15:28 отказ (цикл запущен вручную), в 15:31 и 15:53 после перезагрузок работает.
  Копии от 22:16-22:32 - отказ, в том числе у цикла, стартовавшего при загрузке в 22:30: он скопировал
  заново ещё до первого старта. Как root-настройка даёт право запуска - её область (Миша), не разбираем.
  Если так, то новый демон на ходу не запустить: нужна перезагрузка.
- **Наша ошибка в цикле - копия заново перед каждым стартом.** `cksum` телефона выравнивает CRC по ширине 10
  (`  22166864    2845296 /apps/...`), а `read -r` при чтении `.cksum` срезал ведущие пробелы: при CRC короче
  10 цифр (у сборки 16) строки никогда не совпадали. Отсюда же пауза, которая не росла (новый пакет её
  сбрасывает), и неудача целиком в журнале раз в минуту. У `btctl` CRC из 10 цифр - он не перекопировался.
  Исправлено: `IFS= read -r` (`bbtunneld-boot.sh`, `sync_copies`). Тест цикла теперь с `cksum` в формате
  телефона (CRC из 8 цифр): до правки 22 падения, после - 213 из 213 под dash и bash --posix. На телефоне
  по root-SSH, только чтением: `sh -n` (PD KSH 5.2.14) - ok; с `read -r` - нет совпадения, с `IFS= read -r` -
  совпадение.

**Дальше (Миша):** положить исправленный `bbtunneld-boot.sh` в `/accounts/devuser/rootdata/` не поверх
работающего файла (цикл читает его по ходу): `.new`, потом `mv`. Перезагрузить без Momentics и `connect`.
Цикл должен запустить копию, что уже лежит в RUN (сборка 16, `cksum` 22166864), без строки `copied`. Потом -
профиль с IPv6 по шагам выше; журналы Claude читает сам по root-SSH.

## Как воспроизвести

Конфиг - Cloudflare WARP из `wgcf generate` (`wgcf-profile.conf`, лежит у Миши). Существенное в нём:

```
[Interface]
Address = 172.16.0.2/32, 2606:4700:110:800c:4031:d028:ff5:8e1a/128
DNS = 1.1.1.1, 1.0.0.1, 2606:4700:4700::1111, 2606:4700:4700::1001
MTU = 1280
[Peer]
AllowedIPs = 0.0.0.0/0, ::/0
Endpoint = engage.cloudflareclient.com:2408
```

Импорт «Из файла», включить. Без IPv6 в `Address`, `AllowedIPs` и `DNS` профиль поднимается.

## Где в коде

- `daemon/src/bt_tunnel.c:1096-1105` - адреса назначаются по порядку из конфига, сразу после `bt_tun_open`,
  до `bt_if_mtu` и `bt_if_up`: интерфейс в этот момент ещё не поднят. Сначала IPv4, потом IPv6. Ошибка
  первого же адреса - `fail(t, "tun", ...)`.
- `daemon/src/bt_plat_qnx.c:768` `bt_if_addr` - ветка `family == 6`, попытки - `addr6_try` (строка 741):
  `SIOCAIFADDR_IN6` с `struct in6_aliasreq` (адрес, `ifra_prefixmask`, оба срока `ND6_INFINITE_LIFETIME`).
  До сборки 16 была одна попытка с `IN6_IFF_NODAD` без `ifra_dstaddr` и повтор с `/128` только при
  `cidr != 128`, то есть для `/128` повтора не было.
- Там же: `sa_ip`/`sa_mask` (строка 180), открытие tun с `TUNSIFHEAD` (`bt_tun_open`, строка 635),
  освобождение юнита и `if_destroy`/`if_addrs_clear` (`bt_tun_close`, строка 686).
- IPv4-ветка того же `bt_if_addr` (`SIOCAIFADDR`, дальний конец = свой адрес, повтор без него) на телефоне
  работает.
- Linux-бэкенд (`bt_plat_linux.c:209`) IPv6 назначает без ошибок, e2e в WSL зелёные. QNX-код до
  2026-10-15 был только скомпилирован, на устройстве эта ветка выполнилась впервые.

Заголовки SDK (искать по NDK не надо, долго):
`E:/dev/blackberry/bbndk.win32.libraries.10.3.1.995/target_10_3_1_995/qnx6/usr/include/netinet6/in6_var.h`
(`struct in6_aliasreq`, `SIOCAIFADDR_IN6` - строка 438), рядом `in6.h`, `nd6.h`; `net/if_tun.h` - в
`.../qnx6/usr/include/net/`.

## Устройство

Passport, BB10 10.3.3.3216, стек io-pkt-v6-hc (tun из NetBSD), Wi-Fi - `bcm0`, SIM нет. Демон - от root, из
цикла загрузки (`daemon/boot/bbtunneld-boot.sh`), с аргументами из PLAN §0. `--debug` цикл не передаёт
(аргументы - постоянный контракт, DAEMON §12). Если для разбора нужны строки `BT_D`, это решение:
временная сборка с другим уровнем или новый способ включить отладку - согласовать с Мишей.

## Как доставить новый демон на телефон

1. `bash daemon/build.sh cross`, потом из `BBTunnel/`: `bash ../../bb-shared/tools/build-bar.sh` (buildId
   растёт сам).
2. Миша ставит `.bar`. Цикл загрузки перед следующим стартом сам перекладывает новый `bbtunneld` (по
   `cksum`). Приложение перезапускает старый демон само (APP §9) или Диагностика -> «Перезапустить службу».
3. Журналы: Диагностика -> «Отправить журналы» (цикл загрузки, демон, сервис - одним файлом).

## Готово, когда

- `wgcf-profile.conf` без правок поднимается: «Подключено»;
- `cdn-cgi/trace` показывает `warp=on`; по IPv6 - открыть `http://[2606:4700:4700::1111]/cdn-cgi/trace`,
  там `ip=` должен быть IPv6-адресом;
- выключение профиля снимает адреса и маршруты, следующий туннель снова получает тот же юнит (`tun1`:
  `tun0` держит системный `TunnelManager`, см. результат выше).

Заодно не проверены на телефоне: IPv6-маршруты `::/0` и выход IPv6 к серверу (egress v6). В журнале
IPv4-профиля строки `egress IPv6` нет, IPv6 там не было вовсе.
