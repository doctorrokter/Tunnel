## 0. Коротко

- **Свой клиент Tailscale в демоне**, на C, **только через DERP** - ретрансляторы по TLS/TCP. До NAS за
  CGNAT этого хватает: обе стороны только выходят наружу. Прямые пути (disco, STUN) - потом.
- **Сервер управления - официальный** (`controlplane.tailscale.com`). Headscale - стенд разработки в WSL.
  Из России официальный Tailscale закрыт (§2) - ожидаемо, не чиним.
- **Вход - ключом авторизации** (auth key) из админки Tailscale, вставленным текстом или QR-кодом, **или по
  ссылке** (AuthURL, §11b, демон 0.3.0): телефон показывает ссылку и её QR-код, по ней входят на другом
  устройстве своим аккаунтом.
- **Tailscale - третий тип профиля** рядом с WireGuard и AmneziaWG, во всех сборках: тот же переключатель, те
  же состояния и уведомления. Узлы сети - пиры одного устройства нашего движка, их пакеты идут через DERP.
- **Код - свой, по эталону Tailscale (Go, BSD-3); microlink (C, MIT) - образец раскладки байтов** и источник
  ~1 тыс. строк; как клиент он недоделан (§12). Noise IK собирается на примитивах движка; не хватает только
  ядра Salsa20 для DERP.

## 1. Что должно получиться в первой версии

- Профиль «Tailscale» в своей сети: узлы по адресам 100.x и `fd7a:115c:a1e0::`, NAS за CGNAT доступен с
  Wi-Fi и LTE.
- Вход один раз; ключ узла живёт на телефоне, после перезагрузки профиль поднимается сам (always-on - как у
  остальных).
- На странице профиля - имя сети (tailnet), свой адрес, список узлов: имя, адрес, в сети ли.
- Рядом с Tailscale может быть поднят AmneziaWG или WireGuard - в том числе полный, «весь трафик».
- Во всех сборках, для любой своей сети на официальном сервере.

**Не в первой версии:** ссылка входа, прямые пути (disco, STUN, проброс портов), exit node (весь трафик через
узел сети), MagicDNS (§8), Taildrop, Tailscale SSH, tailnet lock, фильтр пакетов со стороны сервера, свой
сервер управления для других людей. Всё это - доработки поверх того же клиента.

## 2. Сервер управления

**Решено: официальный** (`controlplane.tailscale.com`, бесплатный план) - Миша и NAS не в России.

Из России официальный Tailscale закрыт (`tailscale_gaps_2026-09-30.md` §2): с 2024-10-01 он сам отвечает
российским IP кодом 451 (вход, control, DERP), а провайдеры РФ с июня 2025 вдобавок «замораживают» TLS к
зарубежным хостингам. **Это ожидаемо, и мы это не чиним** (Миша, 2026-09-30). Транспорт Tailscale идёт по
маршрутам (§9), так что внутри поднятого полного AmneziaWG он заработает сам - но специально под это ничего
не делаем.

**Headscale - стенд разработки** в WSL, как ядерный WireGuard для движка (§13): весь путь проверяется без
телефона и без аккаунта. Поэтому адрес сервера управления - всё же поле профиля в демоне: по умолчанию
официальный, другой задаётся только протоколом демона (стенд, `btctl`), в приложении его нет.

**Версия возможностей (capver)** - обещание, какие поля и поведение сервера клиент понимает. Заявляем
**130** (как tailscale-rs; microlink - 131), значение - в настройке. Выполняем обязательства до него, которые
касаются DERP-only: `HomeDERP` и старое поле `DERP` (111), пустые AllowedIPs = Addresses (112), регионы с
`NoMeasureNoHome` не выбираем домашними (115); прочее - неизвестные поля и типы disco - пропускаем.
Порог Headscale растёт с каждым стабильным релизом Tailscale: 130 проживёт до Headscale, собранного после
Tailscale 1.112, дальше - поднять. Текущий стабильный Tailscale - 1.102.5 (capver 142).

Отброшено: заявлять свежий capver 142-148 (больше обязательств - c2n и прочее - без пользы для DERP-only).

## 3. Вход

**Решение: ключ авторизации.** Его создают в админке Tailscale на ПК (на стенде -
`headscale preauthkeys create`) и вставляют в приложение - текстом или QR-кодом (приложение уже умеет QR).
Помощь советует ключ pre-approved и **с тегом**: у устройства с тегом ключ узла не истекает, иначе раз в 180
дней вход заново.

**Ключи и их хранение.** Machine key и node key - X25519, живут в хранилище демона рядом с профилем (как
приватные ключи WireGuard, DAEMON §2), приложению не отдаются. Ключ авторизации отправляется только при
первом входе и не хранится. Истечение node key (ключ без тега) - новый node key с `OldNodeKey`, в UI - «вход
истёк». Disco key - новый при каждом запуске (DERP-only его почти не использует).

**Узел удалён из сети** (0.1.9, 2026-10-22). Удалить узел может админ в консоли, а временный узел (ключ
Ephemeral) Tailscale убирает сам через 30-60 минут офлайн. Так ушёл узел телефона: тестовый ключ Миши был
Ephemeral, Tailscale не включался шесть дней. Официальный сервер на map отвечает тогда «404 node not
found». Демон на любой отказ карты спрашивает control, как Go-клиент при каждом старте: register с ключом
узла без ключа авторизации. По ответу: узла нет (AuthURL или 404) - причина `removed`, «удалено из сети»,
до нового входа; вход истёк - `expired`; узел на месте - map снова после растущей паузы. Проверено на
официальном сервере 2026-10-22 (узел из WSL удалён в консоли): ответ проверки - AuthURL, причина `removed`
через секунду. Headscale удалённому узлу отдаёт карту с ним истёкшим - на стенде это `expired`. Новый вход стирает
кэш адресов профиля: новый узел может получить другие. Помощь и лист входа советуют ключ **не Ephemeral**.
Истёкший ключ авторизации уже вошедшему устройству не вредит (KB 1085): срок у ключа - только на вход.

Отброшено сейчас: ссылка входа (AuthURL) - сервер отвечает ею без ключа, её открывают на ПК, а демон ждёт
повторным register с `Followup`; нужна, когда Tailscale пойдёт к пользователям. OAuth-клиенты - для
автоматизации, не для телефона.

## 4. Где живёт клиент

**Решение: в демоне.** Tailscale - такой же туннель, как WireGuard: tun, маршруты, DNS, движок - всё уже
у демона. Клиент добавляет три части:
- **control** - `/key`, ts2021 (Noise IK), HTTP/2 внутри, register и map (поток netmap с дельтами);
- **DERP** - TLS-соединения к домашнему региону и к регионам пиров, кадры, NaCl box;
- **мост в движок** - пир на узел сети, датаграммы WireGuard идут через DERP (§7).

Демон однопоточный, на `poll` (DAEMON §1); microlink написан на четырёх задачах FreeRTOS с блокирующими
вызовами. У нас всё - неблокирующие конечные автоматы в том же цикле, как DNS-клиент демона: TCP и TLS (с
`POLLOUT`), HTTP/1.1 Upgrade, записи Noise -> поток байт -> EarlyNoise -> HTTP/2 -> control; по клиенту DERP
на регион; применение netmap. Протокол - sans-IO модули `daemon/src/ts_*.c` (тестируются на ПК, как
`bt_resolve`), ввод-вывод - `bt_tls.c` и `bt_tailscale.c`, в цикле `main.c` рядом с `bt_tunnels_*`.

TLS - OpenSSL 3.5.8: сейчас демон линкует только `libcrypto.a`, добавится `libssl.a` (из той же сборки).
Сертификаты проверяются всегда (microlink к DERP ходит без проверки - так нельзя). Корни - свои, встроенные
(ISRG Root X1/X2 и новые Root YE/YR Let's Encrypt), как делает сам `tailscaled`: хранилище BB10 устарело;
плюс `cacert.pem` из bb-shared/net для прочих. Первым шифром - `TLS_CHACHA20_POLY1305_SHA256`: у Krait
(ARMv7) нет AES-инструкций.

Отброшено:
- клиент в приложении или сервисе (Qt): control-канал там был бы проще, но DERP и движок всё равно в
  демоне - вышло бы два процесса на одну сеть и новый протокол между ними; headless-сервис вдобавок живёт в
  лимите памяти лаунчера;
- отдельный процесс-помощник: лишний процесс от root, его запуск и присмотр.

## 5. Протокол

По эталону Tailscale (Go, BSD-3). Раскладка байтов и ссылки на исходники - в заметках разведки.
1. **Ключ сервера** - `GET /key?v=130` по HTTPS.
2. **ts2021.** Официальный сервер - только TLS на 443 (на порту 80 заголовки идут открытым текстом, а 443 -
   запасной путь самого Tailscale); стенд - схема и порт из адреса Headscale. HTTP `POST /ts2021` с
   `Upgrade: tailscale-control-protocol` и первым сообщением Noise в заголовке (initiation - 101 байт, ответ
   - 51), дальше записи Noise по 4 КиБ. Сразу после рукопожатия - преамбула HTTP/2; первые 9 байт входящего
   потока - либо EarlyNoise (`\xff\xff\xffTS`, длина, JSON), либо уже кадр SETTINGS: разбираем оба случая.
   Noise IK собирается на `wg_crypto` (`wg_kdf` - ровно их HKDF), но **nonce записей - big-endian**, не как у
   WireGuard: своя функция кодирования.
3. **HTTP/2** поверх Noise, без TLS: SETTINGS, HEADERS, DATA, WINDOW_UPDATE, PING, GOAWAY. Построители кадров
   - из microlink; **декодер HPACK свой** - microlink статусы не читает, а нам нужны `:status` и
   `Retry-After` (429, 503). Не nghttp2: запросов два, а чужой ввод в процессе root лучше разбирать своим
   коротким кодом под фаззером. Своих PING не шлём (microlink - раз в 5 с, батарея): поток держат KeepAlive
   сервера.
4. **register** - с ключом авторизации только при первом входе; повторное подключение к control - без
   повторной регистрации; истекший ключ узла - новый с `OldNodeKey`. DERP - только после register:
   встроенный DERP Headscale пускает лишь зарегистрированные ключи.
5. **map** - потоковый, `Stream:true, KeepAlive:true`, без zstd: первый полный netmap, затем дельты
   (`PeersChanged`, `PeersRemoved` и `PeersChangedPatch` - по NodeID и массивом; microlink разбирает их
   неверно), `OnlineChange`. Сообщения длиннее одной записи Noise собираются из нескольких (microlink их
   теряет). Сторож: от control ничего 120 с - переподключение.
6. **JSON - jsmn** (MIT, ~500 строк): токены поверх самого буфера, без выделения памяти, плюс наш разбор
   нужных полей (Node, DERPMap, свои адреса, имя сети). Не cJSON: его дерево в разы больше самого netmap
   (десятки-сотни КБ). Всё - под фаззером: вход чужой, процесс - root.

## 6. DERP

- TLS к узлу региона на `DERPPort` (0 - это 443), HTTP `Upgrade: DERP`; ServerKey, ClientInfo, ServerInfo,
  NotePreferred. **ClientInfo - NaCl box** в формате `crypto_box_easy`: наш ключ 32 байта, nonce 24, тег
  Poly1305 16, шифротекст JSON (`version`, `meshKey`, `CanAckPings`, `IsProber`, `AppName` - три последних
  с заглавной). Ядра Salsa20 в OpenSSL нет: HSalsa20 и XSalsa20 (по TweetNaCl) - отдельный модуль движка
  `wg_salsa` с векторами NaCl и `x/crypto/nacl`; Poly1305 - из OpenSSL (`EVP_MAC "POLY1305"`), X25519 - `wg_dh`.
- SendPacket / RecvPacket по node key, KeepAlive, Ping/Pong, PeerGone.
- **Сертификат** - цепочка к встроенным корням. Пин `sha256-raw:` из DERPMap (`CertName`) - только для
  стенда: так проверяется TLS со своим `derper` без домена (§13).
- **Домашний регион** - выбираем сами: время TLS-соединения к первому узлу каждого региона из DERPMap,
  лучший - наш (кроме `NoMeasureNoHome`), его отдаём в `PreferredDERP`; заново - при смене сети. (microlink
  зашил регион 9 - Даллас.)
- Пакеты адресуются в пределах региона: для пира с другим домашним регионом - соединение к его региону
  (microlink регион пира хранит, но не использует - и до таких пиров не достаёт). Закрываем после 60 с без
  трафика.
- Рукопожатие WireGuard начинаем и сами: пакет из DERP будит пира на той стороне (у Tailscale -
  `noteRecvActivity`).
- Имена узлов DERP - через DNS-клиент демона (`bt_resolve`), как Endpoint у WireGuard.
- Обрыв - переподключение с отступом; смена сети (DAEMON §7) - переподключение сразу.
- Скорость через публичный DERP ограничена (ServerInfo сообщает лимит), трафик шифруется дважды
  (WireGuard внутри TLS). Для NAS хватит; прямые пути - потом.

Отброшено сейчас: HTTP-прокси (`CONNECT`) и DERP поверх WebSocket - они для сетей, где прямой TLS режут; для
себя не нужны.

## 7. WireGuard поверх DERP

Один туннель Tailscale - одно устройство движка со своим tun, MTU 1280 (как у Tailscale), кодек - обычный
WireGuard. Узел сети - пир: публичный ключ = `Node.Key`, AllowedIPs = `Node.AllowedIPs` (пусто - его
Addresses).

**Решение: пир передаётся в upcall отправки.** В `wg_device` - необязательный upcall `send_peer(ctx, пир,
...)`: задан - движок зовёт его вместо `send`, и демон сам решает, куда слать (в соединение DERP региона
пира; позже - проверенным прямым путём), как `magicsock` у Tailscale. Endpoint у всех пиров Tailscale - одна
постоянная метка (`WG_EP_OWNER`), роуминг движка ничего не двигает. Приём: RecvPacket от ключа X -> пир X
-> `wg_device_receive_from`. Цена: ~130 строк в движке с комментариями, и тесты; пять пользователей старого
`send` не меняются. Пакеты disco (префикс `TS💬`) в движок не идут.

Отброшено: «адрес DERP» в `wg_endpoint` (движок без правок, но смысл endpoint перегружен, и роуминг
`heard()` может увести пира на чужой адрес); восстанавливать пира из указателя на endpoint (молча сломается
при любой правке движка).

**Ещё в движке и демоне для больших сетей** (`microlink_port_2026-09-30.md` §6):
- пул узлов AllowedIPs отдаётся только пустой таблице - нужна функция «переехать в больший пул» (узлы
  адресуются индексами - ~15 строк);
- кольцо ожидания 32 КБ на пира - для сотни пиров 3,2 МБ. Пиров добавляем лениво, как сам Tailscale:
  `WG_DROP_NO_ROUTE` -> демон находит узел по адресу назначения в netmap, добавляет пира, повторяет;
- по желанию `wg_device_receive_from(пир)` - индекс за O(1) и проверка «пакет из DERP от ключа X - пир X».

## 8. Сеть телефона

- Адреса узла: `100.x.y.z/32` и `fd7a:115c:a1e0::/128` - на tun, как Address у WireGuard.
- Маршруты: `100.64.0.0/10` и `fd7a:115c:a1e0::/48` в tun - раздельный туннель, рядом с полным AmneziaWG
  или WireGuard; подсети за узлами (subnet router) - если их несут AllowedIPs.
- **DNS:** без MagicDNS в tailnet не трогаем - к NAS по адресу 100.x. С MagicDNS (имена `*.ts.net` и
  узлов) - свой ответчик демона на `100.100.100.100`, §8a (сделано 2026-10-16, демон 0.1.4).

## 8a. MagicDNS (утверждено Мишей 2026-10-16: «делаем, но максимально аккуратно»; сделано, демон 0.1.4)

Цель: `http://nas:5000` и `nas.<tailnet>.ts.net` открываются на телефоне, как в официальном
клиенте, а все остальные имена работают как без Tailscale.

**Как у tailscaled:** свой резолвер на `100.100.100.100` (и `fd7a:115c:a1e0::53`), внутри tailnet. У BB10 нет
split-DNS, поэтому системный DNS (`_CS_RESOLVE`) указывает на него, а он сам решает, что отвечать.

1. **Где отвечает.** Адрес `100.100.100.100` уже попадает в маршрут `100.64/10` в tun. UDP на порт 53 к нему
   демон не отдаёт ни одному узлу, а отвечает сам: читает запрос из tun, пишет ответ в tun. Свой сокет не
   нужен, порт 53 не занимаем.
2. **Что отвечает сам.** A и AAAA имён узлов netmap: `Name` узла (`nas.tailXXXX.ts.net.`) - его адреса
   100.x и fd7a. Короткое `nas` - через домен поиска: в `_CS_RESOLVE` идёт `search tailXXXX.ts.net`
   (первый из `DNSConfig.Domains`), резолвер телефона сам допишет его к короткому имени. `ExtraRecords` из
   DNSConfig - тоже. Имя tailnet, которого нет в netmap, - NXDOMAIN, не пересылка.
3. **Остальное пересылает** туда, куда шёл бы DNS без Tailscale: серверам полного туннеля, если он поднят
   (WARP, AmneziaWG - `DNS=` его `.conf`), иначе серверам сети (Wi-Fi, из PPS). Ответ кладётся обратно в tun
   спросившему. Свой UDP-сокет пересылки - как у остальных сокетов демона (обход туннелей там, где сервер
   сети, или внутрь полного туннеля, где его DNS).
4. **«Override local DNS» в админке** (`DNSConfig.Resolvers` непустой) - пересылать им, а не серверам сети.
   Split DNS (`DNSConfig.Routes`: домен -> свои серверы внутри tailnet) - не в этом шаге.
5. **Когда включается.** Только если в tailnet MagicDNS включён (`DNSConfig.Proxied`); выключен - DNS не
   трогаем, как сейчас. Туннель Tailscale опущен - системный DNS как без него (сегодняшний `dns_reconcile`).
   Свои запросы демона (control, DERP, имена серверов) идут мимо `100.100.100.100` - прямо тем серверам,
   куда он пересылает: иначе петля.
6. **Проверка.** Стенд: Headscale с `magic_dns: true` и своим `base_domain`; в namespace телефона
   `getent hosts nas`, `nas.<base>`, внешнее имя через заглушку DNS, с полным WireGuard рядом - через его DNS;
   юнит-тест разбора и сборки DNS-сообщений с фаззером, как у остального. Телефон: NAS по имени в браузере,
   с WARP и без.

Объём - примерно день: разбор `DNSConfig` в netmap, ответчик и пересылка в демоне, `dns_reconcile` с
Tailscale, стенд, тесты. Приложение не меняется (разве что показать на странице профиля, что MagicDNS
включён).

**Как сделано (2026-10-16, демон 0.1.4).** Всё по пунктам выше, с такими уточнениями:

- **Модули.** `ts_netmap` разбирает `DNSConfig` (Proxied, Resolvers, Domains, ExtraRecords A/AAAA) - сообщение
  с испорченным DNSConfig отвергается целиком, как любое другое. `ts_dns` - ответчик без ввода-вывода: IP/UDP
  пакет из tun -> ответ (A, AAAA, NXDOMAIN, NOTIMP, FORMERR, SERVFAIL, TC для длинного) или запрос наверх;
  ответ сверху сверяется по id и хешу вопроса, отпускается через 5 с; не больше 64 запросов в пути.
  `bt_tailscale` - имена из netmap, сокеты пересылки (неблокирующие, по маршрутам, ответы только от тех
  серверов, кому слали, с порта 53), смена сервера после потерянного запроса.
- **Имена.** Узел - по `Name` из netmap, без учёта регистра и точки в конце. Короткое имя - как
  `<имя>.<домен tailnet>`; не нашлось - пересылается как есть (в сети может быть такой хост). Имя внутри домена
  tailnet, которого никто не носит, - NXDOMAIN сразу.
- **Системный DNS.** `[100.100.100.100, затем серверы, которые были бы без MagicDNS]` - не больше трёх (резолвер
  читает первые три): DNS= полного туннеля, иначе серверы сети. Второй сервер - запасной: демон упал, tun и
  маршрут пропали - имена резолвятся дальше, как без Tailscale (на стенде - 5 с ожидания на первом сервере);
  журнал при следующем старте возвращает системный DNS, туннель ставит MagicDNS снова. Поиск: домен tailnet,
  `DNSConfig.Domains`, затем домены полного туннеля - целыми словами, не больше 6 и 255 символов (что читает
  резолвер). В `_CS_RESOLVE` - только IPv4 `100.100.100.100`; на `fd7a:115c:a1e0::53` ответчик тоже отвечает.
  Строка - без единого пробела, домены тоже через `_`
  (`nameserver_100.100.100.100_nameserver_192.168.1.1_search_tailb78ad.ts.net`): с пробелом система отвечает
  `EINVAL`, и на сборке 21 (демон 0.1.4) MagicDNS из-за этого не встал - исправлено в 0.1.5. Откажет и так -
  серверы ставятся без доменов поиска.
- **Но резолвер BB10 `_CS_RESOLVE` не читает** (сборка 22 на телефоне: строка на месте, к `100.100.100.100` ни
  запроса). Он берёт `nameservers` и `searchdomains` из PPS `/pps/services/networking/status_public`, которым
  владеет `net_pps`. С демона 0.1.6 (сборка 23) системный DNS - эти два атрибута; `_CS_RESOLVE` - копия для
  старых программ. Опыт вручную на телефоне: `ping nas` -> `nas.tailb78ad.ts.net
  (100.69.167.72)`, ответы NAS. Как демон уживается с `net_pps` - `daemon/README.md`, раздел QNX.
- **Кто владеет DNS.** Как раньше: туннель WireGuard с `DNS=` (полный - первым); Tailscale с MagicDNS (поднятый
  последним) ставит свой ответчик перед ним. Хук `resolvers` (имена control и DERP, пересылка) остаётся
  прежним - никогда не `100.100.100.100`.
- **Выключение.** Вход истёк, туннель упал или опущен, MagicDNS выключен в админке - системный DNS
  возвращается в тот же проход цикла (`stop` -> `dns_refresh` -> `dns_reconcile`).
- **Проверено.** Юнит-тесты `test_ts_dns` (299 тыс. проверок с фаззером) и `test_ts_netmap` (DNSConfig и
  атомарность отказа). Стенд, этап A с `magic_dns: true` (`STAND_MAGIC=1`): короткое и полное имя, IPv6,
  своё имя, ExtraRecords, NXDOMAIN сразу, пересылка к заглушке сети, новый узел по имени (дельта), после
  смены сети, внутри полного WireGuard (ядерный сервер в `ts-inet`, его DNS виден только через туннель),
  демон убит (запасной сервер), журнал, истечение входа, удаление - 67 из 67. Этап B - MagicDNS выключен:
  DNS не тронут - 45 из 45. Код приложения против демона (`client`) - WireGuard и Tailscale на обоих этапах.
  Настоящий Tailscale Миши (`SAAS_NAME=nas saas.sh KEY 100.69.167.72`): «MagicDNS on, domain
  tailb78ad.ts.net», resolv.conf `100.100.100.100, 1.1.1.1, 8.8.8.8` + `search tailb78ad.ts.net`, `nas`
  -> 100.69.167.72, ping по имени, `controlplane.tailscale.com` - через пересылку.
- **Раздельный DNS (split DNS, демон 0.2.0, список Миши 2026-10-22).** `DNSConfig.Routes` разбирается как
  `Unmarshal` (не объект, не массив, плохой Resolver - отказ всего сообщения): суффикс без точки в нижнем
  регистре, до 4 простых DNS-серверов на маршрут, до 128 маршрутов. Пустой список - «отвечает сам
  MagicDNS» (имена tailnet и ExtraRecords, иначе NXDOMAIN); только DoH и подобное - SERVFAIL: имя не уйдёт
  на серверы, для которых не предназначено. Резолвер: свои имена и NXDOMAIN своего домена - как раньше,
  затем маршрут с самым длинным подходящим суффиксом (как форвардер Go) - его серверы (их адреса бывают в
  tailnet: сокет пересылки идёт по маршрутам), иначе серверы по умолчанию. **Сервер управления (и
  Headscale) сам шлёт 65 маршрутов** - обратные зоны `100.64/10` (64 зоны `NNN.100.in-addr.arpa`) и
  `fd7a:115c:a1e0::/48`, все MagicDNS'ные: с прежним пределом 16 маршрут tailnet в них тонул; PTR под ними
  теперь NXDOMAIN сразу (у Go - имя узла; пока нет). Только при включённом MagicDNS. Журнал: «split DNS:
  corp.split -> 10.20.0.5; 65 MagicDNS's own». Стенд A, раздел 2b: имя под маршрутом - от его сервера (сеть
  знает то же имя с другим адресом), чужого под маршрутом нет - NXDOMAIN, соседнее имя - к резолверу сети.
- **Не сделано:** ответ PTR на адреса tailnet; `fd7a:115c:a1e0::53` в `_CS_RESOLVE`; DNS оператора в
  `100.64/10` (так бывает у CGNAT) маршрут tailnet уводит в tun и без MagicDNS - пересылка к нему не дойдёт.

## 9. Транспорт Tailscale и другие туннели

Транспорт Tailscale - TLS к control и DERP - обычный трафик телефона. **Решение: не привязывать его к
физическому интерфейсу** (в отличие от UDP-сокетов WireGuard, DAEMON §5): он идёт по маршрутам. Поднят
полный AmneziaWG или WireGuard - control и DERP уходят внутрь него, нет - идут напрямую. Ничего особого для
этого писать не нужно; так Tailscale заработает и из России (§2), если когда-нибудь понадобится. Падение или
подъём полного туннеля для Tailscale - как смена сети: переподключение.

## 10. Профиль и экраны

- **Тип профиля `tailscale`** в хранилище демона: machine key, node key (и старый), адрес сервера управления
  (официальный; другой - только на стенде), последний netmap (чтобы после перезагрузки подниматься, не
  дожидаясь control).
- **Добавить** - в том же листе, отдельный источник «Tailscale»: поле ключа авторизации - текст или QR.
  Протокол демона: `profile.import type=tailscale authkey=...` (+ `control=` на стенде).
- **Строка списка и страница профиля** - как у WireGuard, плюс имя сети, свой адрес 100.x и список узлов
  (имя, адрес, в сети). Состояния те же; добавится причина `expired` - вход истёк (ключ без тега) или ключ
  отвергнут.
- **Уведомление сервиса** «вход истёк» - по тем же правилам, что «связь потеряна».
- Строки - с переводами RU и PL, как всё приложение: дешевле сразу, чем потом.

## 11. Что не в первой версии - и как потом

- **Прямые пути** (disco ping/pong, CallMeMaybe, STUN): DERP остаётся запасным, прямой UDP - оптимизация; на
  сотовой сети с жёстким NAT он часто и не нужен. Проект - §11a (2026-10-16, Миша: «надо делать, не дело
  ходить через Франкфурт до NAS, который у меня дома»).
- **Ссылка входа** (AuthURL, текстом и QR) - когда Tailscale пойдёт к пользователям.
- **Exit node** - весь трафик через узел сети: тот же конфликт «весь трафик», что у полных профилей (APP §3).
- **Taildrop**, **SSH**, **tailnet lock** - по запросу. MagicDNS сделан (§8a), split DNS тоже (§8a, 0.2.0).

## 11a. Прямые пути - проект (на утверждение, 2026-10-16)

Цель: телефон и узел tailnet говорят напрямую по UDP, когда это возможно - дома по Wi-Fi (NAS в той же сети,
192.168.1.x), вне дома через интернет, если NAT обеих сторон пропускает. DERP остаётся: с него всё начинается,
на него всё возвращается, если прямой путь пропал. Сегодня до NAS ~4 Мбит/с через два ретранслятора
(PLAN §0, замер 2026-10-16); дома по прямому пути ожидается скорость Wi-Fi.

**Как у официального клиента** (эталон `refs/tailscale` 1.102.5, `wgengine/magicsock`, `disco`, `net/stun`):

- Один UDP-сокет и один порт на всё: STUN, служебные пакеты disco и WireGuard. Входящий датаграм разбирается
  по виду: ответ STUN, disco (магия `54 53 f0 9f 92 ac` "TS💬"), остальное - WireGuard.
- **disco**: `магия[6] | disco-ключ отправителя[32] | nonce[24] | NaCl box` (Curve25519 + XSalsa20-Poly1305,
  тег впереди - ровно наш `wg_box_*`), внутри `тип[1] версия[1] тело`. Нужны три сообщения: Ping (TxID[12] +
  node key отправителя[32]), Pong (TxID[12] + адрес, с которого пришёл ping: IP[16] + порт[2]), CallMeMaybe
  (список адресов по 18 байт; только через DERP). Остальное (Bind/Allocate - peer relay, Geneve) молча
  отбрасывается.
- **Пиры переходят на прямой путь только по pong**: узел пингует наши адреса, получил pong - шлёт нам напрямую
  и доверяет пути 6,5 с; пока сессия активна (трафик за 45 с), пингует каждые 3 с. Не отвечаем - через 6,5 с
  снова шлёт через DERP (и по UDP заодно) и пингует всё заново. Наш WireGuard по UDP его путь не меняет.
- **Наши адреса пир узнаёт** из netmap (мы шлём `Endpoints` и `EndpointTypes` в коротком map-запросе
  `OmitPeers:true`; в потоковом сервер их не читает), из CallMeMaybe через DERP и из ping, пришедшего от нас.
  Адреса: локальные адреса интерфейсов с портом сокета (тип 1) и внешний адрес из STUN (тип 2).
- **STUN**: binding request (`00 01`, cookie `21 12 a4 42`, TxID[12], SOFTWARE "tailnode", FINGERPRINT) на
  `STUNPort` узла из карты DERP (0 = 3478); ответ - XOR-MAPPED-ADDRESS. Повтор каждые 20-26 с, пока есть
  трафик; простой больше 45 с - не повторять.
- Пути выбираются по задержке pong; частные адреса и IPv6 с бонусом; смена - только при выигрыше больше 1 %.

**Что у нас уже есть** (разведка 2026-10-16): disco-ключ делается при каждом старте и уже уходит в map-запросах
(`bt_tailscale.c`); netmap разбирает `DiscoKey` пиров; NaCl box есть (`engine/src/wg_salsa.*`: `wg_box_beforenm`,
`wg_secretbox_seal/open`); путь пакета к пиру выбирает один `bt_ts_send_peer`, а входящий WireGuard уже идёт в
движок через `wg_device_receive_from` - движку менять, по разведке, нечего. Нет: `Endpoints` пиров в netmap,
наших `Endpoints` в map-запросе, UDP-сокета у туннеля Tailscale, STUN, disco кроме отбрасывания.

**Что сделать:**

1. **`ts_disco`** (без ввода-вывода): упаковка и распаковка Ping, Pong, CallMeMaybe; ключ пира - один
   `beforenm` на пира. Векторы - генератор на Go из `refs/tailscale/disco` (как у netmap), фаззер.
2. **`ts_stun`** (без ввода-вывода): запрос и разбор ответа, векторы из `net/stun`, фаззер.
3. **`ts_path`** (без ввода-вывода): у каждого пира - адреса-кандидаты (из netmap, из CallMeMaybe, из пришедших
   ping; не больше 16), когда кого пинговать (не чаще раза в 5 с на адрес), лучший адрес и до какого времени
   ему верим (6,5 с от последнего pong), heartbeat раз в 3 с при активной сессии, когда слать CallMeMaybe.
   Таблицы ограничены, всё по часам демона; тесты на время (как `ts_dns`).
4. **netmap**: `Node.Endpoints` и `Endpoints` в патчах - в узел (арена, не больше 16 адресов).
5. **Наши адреса**: локальные IPv4 физических интерфейсов (не tun) с портом сокета + адрес из STUN; в короткий
   map-запрос при старте и при каждой смене набора.
6. **Сокет**: один UDP (IPv4) на туннель Tailscale, порт случайный на запуск. Демон отвечает на каждый ping
   pong-ом (туда же, откуда пришёл, - UDP или DERP), пингует кандидатов пира, когда шлёт ему, а прямого пути нет,
   и шлёт CallMeMaybe через DERP. `bt_ts_send_peer`: есть доверенный прямой адрес - UDP, нет - DERP, как сейчас.
   Входящий WireGuard по UDP - в движок; чужой адрес - движок сам находит пира по рукопожатию.
7. **Смена сети**: всё прямое сбрасывается, STUN заново, новые адреса - в map; до pong - DERP.

**Решения на утверждение:**

- **(1) Прямой UDP при поднятом WARP - по маршрутам**, как транспорт Tailscale (§9): внутрь WARP; дома NAS в
  локальной подсети, её маршрут точнее маршрутов WARP - путь по Wi-Fi есть и так. Вне дома прямой путь через
  NAT Cloudflare может не пробиться - тогда DERP, как сейчас. Обход WARP (как сокеты WireGuard) возможен, но
  тогда трафик к NAS выйдет мимо WARP; не предлагаю.
- **(2) Только IPv4** в первой версии: дома у телефона IPv6 нет (`ip6_ok::error_no_ip_addr`). IPv6 - потом.
  (Сделано в 0.2.0, ниже.)
- **(3) Без** port mapping (UPnP / NAT-PMP / PCP), peer relay, MTU-проб: на прямой путь дома не влияют.
- **(4) Этапы**: сначала прямой путь в локальной сети (адреса интерфейсов, disco, путь) - это и есть «NAS дома
  через Франкфурт»; затем STUN и путь через интернет. Оба - в одну версию демона, если первый пройдёт стенд.

**Батарея.** Пинги (раз в 3 с) и STUN (раз в 20-26 с) - только пока есть трафик к узлу; простой 45 с - тишина,
как у официального клиента. Без трафика расход как сейчас.

**Безопасность.** disco от ключа, которого нет в netmap, отбрасывается (как в эталоне); ответ STUN принимается
только от сервера, которому слали, с тем же TxID; WireGuard по UDP проверяет сама криптография движка. Таблицы
и очереди ограничены; любой сбой прямого пути - назад на DERP, туннель не падает.

**Проверка.** Стенд (§13): `TS_DEBUG_ALWAYS_USE_DERP` - параметром узла (сейчас он выключает у `tailscaled`
UDP совсем). Сценарии: общая «домашняя» сеть телефона и NAS (мост между namespace) - путь по ней; маршрутизируемый
«интернет» (forwarding в `ts-inet`) - прямой путь без NAT; NAT-роутер (nft masquerade) - путь через адрес из
STUN; «жёсткий» NAT (masquerade fully-random) - остаётся DERP; правило drop посреди сессии - назад на DERP за
~7 с и снова прямой, когда drop снят; смена сети. Официальный `tailscale status` у NAS должен показать
`direct`. Телефон: `tailscale status` на ПК или NAS - телефон `direct 192.168.1.93:<порт>`; скачивание с NAS -
скорость Wi-Fi.

**Объём**: 3-5 дней - три модуля без ввода-вывода с векторами и фаззерами, netmap, сокет и путь в
`bt_tailscale`, стенд с мостом и NAT, телефон.

**Утверждено Мишей 2026-10-17** («с четырьмя решениями, максимально аккуратно, сначала локальная сеть»).
**Этап 1 - локальная сеть - сделан (демон 0.1.8):**

- `ts_disco` (без ввода-вывода): Ping, Pong, CallMeMaybe - рамка, NaCl box под общим ключом пары, разбор как
  `disco.Parse` (Ping без ключа и с заполнением от 32 байт читается как без ключа и с заполнением на 32
  меньше - на проводе их не отличить, Go так же). Векторы - `daemon/test/vectors/disco` (Go, эталонные
  `disco` и `nacl/box`, nonce фиксирован): 19 рамок, наши запечатанные совпадают байт в байт; фаззер.
- `ts_path` (без ввода-вывода): правила `endpoint.go` по одному - кандидаты (из CallMeMaybe и адреса пингов;
  адреса из netmap - функция есть, разбор `Node.Endpoints` пока не подключён), круг пингов раз в 5 с на адрес
  и CallMeMaybe после круга, лучший по pong (`betterAddr`: очки скорости, +20 частный, +10 IPv6, без смены
  меньше 1 %), доверие 6,5 с, heartbeat раз в 3 с пока сессия активна (45 с), полный круг при конце доверия

- `bt_tailscale`: UDP-сокет IPv4 на туннель (порт ядра, по маршрутам); наши адреса - IPv4 интерфейса

  смене; disco по UDP и через DERP (Ping -> Pong туда же, откуда пришёл; через DERP - с `127.3.3.40:<регион>`
  как у magicsock; CallMeMaybe - только через DERP); WireGuard по прямому пути - в движок с меткой владельца,
  как из DERP (движок не менялся); `tailscale.nodes` даёт `direct=<адрес>`; в журнале «X directly at A (N ms)»
  и «X through the relays again».
- **Отступление от проекта:** адреса узла из netmap (`Node.Endpoints`) пока не разбираются - узел присылает
  их сам в CallMeMaybe, как только видит наши у сервера управления, а его ping приходит с его адреса. Стенд

## 11c. Exit node - весь трафик через узел сети - проект (отложен Мишей 2026-10-23: «пока не делаем, оставляем в плане»)

Цель: весь трафик телефона - через выбранный узел tailnet (NAS дома, ПК), как полный туннель WARP.

**Как у официального клиента** (эталон 1.102.5):
- Узел-выход объявляет `0.0.0.0/0` и `::/0` (`Hostinfo.RoutableIPs`); после одобрения они в его
  `AllowedIPs`. Выходом годится узел с обоими /0 (`tsaddr.ContainsExitRoutes`). Выбор клиент сообщает
  в `Hostinfo.ExitNodeID`.
- /0 получает только выбранный узел (`routemanager.eligible`) - и в маршрутах, и в его AllowedIPs
  WireGuard. Маршруты ОС: оба /0 в tun; локальная сеть - мимо tun только при `ExitNodeAllowLANAccess`
  (по умолчанию - тоже в tun, «чтобы не было утечки»).
- Свой транспорт (control, DERP, STUN, прямой UDP) - мимо туннеля (`netns`: на Linux метка сокета, на
  Windows/macOS привязка к интерфейсу).
- DNS: серверы по умолчанию - DoH выхода по его peerAPI (`POST http://<выход>:<peerapi>/dns-query`), если
  выход умеет (`peerapi-dns-proxy`); иначе `FallbackResolvers`. Маршруты split DNS - только с
  `UseWithExitNode`.
- **Закрыто при сбое:** выход пропал - /0 остаются, трафик в никуда, мимо не идёт.

**Что у нас уже есть:** `ts_netmap_node_routes` и `ts_netmap_os_routes` принимают `exit_node`; полный
туннель с привязкой транспорта к интерфейсу выхода (FIB 15 / `SO_BINDTODEVICE`) - у WireGuard (WARP);
конфликт «другой профиль ведёт весь трафик» - в приложении.

**Что сделать:**
1. Демон: в профиле Tailscale - выбранный выход (`exit_node=`, по StableID) и «локальная сеть мимо»;
   туннель Tailscale с выходом - полный (/0 в tun, как WARP; конфликт с другим полным - как сейчас);
   транспорт Tailscale - привязан к интерфейсу выхода (сейчас он идёт по маршрутам, §9); `ExitNodeID` в
   Hostinfo; выход пропал - /0 остаются (закрыто).
2. DNS при выходе: DoH к peerAPI выхода (HTTP/1.1 по TCP через tun, POST `application/dns-message`) - новый
   небольшой клиент; без DoH у выхода - `FallbackResolvers`, иначе SERVFAIL (не мимо).
3. Приложение: на странице профиля - «Выход в интернет через...» со списком годных узлов (в сети или нет),
   «Не через узел», «Локальная сеть мимо выхода»; строка состояния - «через NAS».
4. Стенд: официальный `tailscaled` с `--advertise-exit-node` (Headscale - одобрить маршрут), «интернет»
   только за ним: телефон достаёт его, транспорт мимо, DNS через выход, выход упал - мимо ничего.

**Решения на утверждение:** (1) транспорт Tailscale привязывать к интерфейсу только при выходе (без
выхода - по маршрутам, как сейчас: внутрь WARP); (2) локальная сеть по умолчанию - в выход, как у Go;
(3) закрыто при сбое; (4) с выходом нельзя одновременно WARP (один полный туннель). **Объём:** 5-7 дней.

## 11d. Taildrop - файлы между устройствами - проект (отложен Мишей 2026-10-23: «пока не делаем, оставляем в плане»)

Цель: принять файл с ПК или телефона сети («Отправить через Taildrop») и отправить файл с телефона на
устройство сети.

**Как у официального клиента** (эталон 1.102.5, `feature/taildrop`, `ipnlocal/peerapi.go`):
- **peerAPI** - HTTP/1.1 (и h2c) на своём адресе tailnet, порт `(32<<10) | crc32` трёх последних байт
  адреса; объявляется в `Hostinfo.Services` (`peerapi4`, `peerapi6`). Кто звонит - только по адресу
  источника в tailnet; нет такого узла - отказ. Запрос с `Referer` или `Origin` - 403; `Host` - `peer` или
  свой адрес.
- **Приём** - `PUT /v0/put/<имя>`: отправитель - тот же пользователь и оба без тегов, или у него грант
  `https://tailscale.com/cap/file-send`; у нас самих - `https://tailscale.com/cap/file-sharing` в CapMap
  (включено в сети). Имя - UTF-8, без `/ \ : * " < > |`, не больше 255 байт; занятое имя - «имя (1).ext».
  `Range: bytes=N-` - докачка; `GET /v0/put/<имя>` - хеши частей (необязательно: 404/405 - докачки нет).
- **Отправка** - кому: тот же пользователь или грант `https://tailscale.com/cap/file-sharing-target`; есть
  peerapi; `PUT` на `http://<узел>:<peerapi>/v0/put/<имя>` с `Host: peer`.

**Важно для Миши:** телефон теперь с тегом `tag:phone` (вход без истечения). Устройству с тегом без правила
доступа (grant `file-send` / `file-sharing-target` в ACL) Taildrop файлы не шлёт и от него не принимает.
Нужна строка в политике tailnet - или вход телефона без тега (тогда вход истекает раз в 180 дней).

**Что сделать:**
1. Демон: peerAPI на своём адресе tailnet (TCP слушает ядро через tun); разбор запроса HTTP/1.1 - новый
   модуль без ввода-вывода, с пределами (заголовки, имя, одновременно два приёма, тайм-ауты); права - по
   узлу из netmap и грантам (`PacketFilter` CapGrant - сейчас не разбираем); запись - в
   `shared/downloads/Taildrop/` через `.partial`, `O_EXCL | O_NOFOLLOW`, владелец - пользователь телефона;
   место на диске - приём отклоняется, если после него останется меньше 200 МБ. Событие клиенту.
2. Отправка: из приложения (карточка «Поделиться» -> «Tunnel: на устройство...») -> демон читает файл и
   шлёт `PUT` через tun.
3. Приложение и сервис: уведомление в Hub «Файл от ПК: имя», открыть, папка; цель «Поделиться».
4. Стенд: официальный `tailscale file cp` на телефон и с телефона на `tailscale file get`; без гранта -
   403; имя с `/` - 400; место кончается - отказ.

**Решения на утверждение:** (1) папка `shared/downloads/Taildrop`; (2) без докачки в первой версии; (3)
порог свободного места 200 МБ; (4) теговый телефон - через grant в ACL (опишем строку). **Объём:** 5-7
дней.

## 11e. SSH к телефону - предложение (на обсуждение, 2026-10-23)

Tailscale SSH - свой SSH-сервер в клиенте (ключи не нужны, права - политикой `ssh` в ACL). Для нас это
полноценный SSH-сервер на C с оболочкой - от root (демон root) - в сеть: большой объём и главный риск
проекта. **Предлагаю не делать:** root-sshd телефона слушает все адреса (`ListenAddress` не задан, bb-shared
README) - значит, по адресу телефона в tailnet (100.114.0.124:22) SSH уже доступен с любого устройства
сети по ключу, как по Wi-Fi. **Проверено 2026-10-23 (сборка 31):** `netstat -an` на телефоне - `*.22` и
`tcp6 *.22` в LISTEN, то есть и на 100.x tailnet. Следствие: SSH телефона виден каждому устройству сети -
доступ ограничивают ключи sshd и ACL tailnet. Если нужен вход именно «по аккаунту Tailscale» - обсудим
отдельно: какой пользователь, какая оболочка, какие права.

## 12. microlink: что берём

Склонирован в `refs/microlink` (@216da330, только для чтения, как amneziawg-go). Лицензии: всё нужное - MIT
(NaCl box - по TweetNaCl, public domain; x25519 - MIT); копилефта нет. Разбор по файлам -
`microlink_port_2026-09-30.md`. Коротко:
- **почти как есть** (~1 тыс. строк): Salsa20 и NaCl box, построители кадров HTTP/2, шаблоны JSON запросов;
- **образец шаг в шаг** (~1 тыс.): Noise IK, рукопожатие DERP, порядок register и map;
- **не берём** (~4 тыс. и платформа): STUN, disco, обвязку lwIP и wireguard-lwip, задачи FreeRTOS.

**README обещает больше, чем делает код** - поэтому образец, а не основа: ключ control зашит (с Headscale не
работает), регион DERP зашит, к регионам пиров не подключается, дельты netmap разбирает неверно, длинные
сообщения теряет, HTTP-статусы и AuthURL не знает, истечение ключа узла не лечит, TLS к DERP без проверки
сертификата. Эталон поведения - исходники Tailscale.

Своего кода выйдет ~4,5-5,7 тыс. строк C и ~2 тыс. строк тестов - это и есть работающий клиент.

## 13. Стенд разработки

В WSL, как e2e демона: сетевые namespace «телефон», «интернет» и «NAS». Headscale 0.29.4, `derper` и
`tailscaled` собираются Go, который в WSL уже есть; модули Go качаются из сети - минуты.
- **Этап A - без TLS:** Headscale с `server_url` = `http://<IP стенда>:8080`, встроенный DERP, пустой

  `TS_DEBUG_ALWAYS_USE_DERP=1` (ведёт себя как наш DERP-only), вход по reusable pre-auth key, `--login-server`

**[телефон]**.

## 15. Риски

- **Протокол меняется.** capver - обещание; заявляем честный 130 и поднимаем, когда Headscale поднимет порог
  (после Tailscale 1.112); перепроверяем с каждым релизом. Что официальный сервер меняет в ответах по capver
  - закрытый код, только опытом.
- **Память демона.** Netmap - десятки-сотни КБ JSON: jsmn без дерева, ленивые пиры, маленькое кольцо
  ожидания. Лимиты демона на телефоне - открытый вопрос PLAN §4 **[телефон]**.
- **Батарея.** Два долгих TCP (control и DERP); своих пингов нет, держат KeepAlive серверов (DERP - раз в
  60 с). Расход замерить **[телефон]**.
- **Скорость** через публичный DERP ограничена и шифруется дважды. Для NAS хватит.
- **Условия Tailscale** запрещают реверс-инжиниринг «Сервисов», о сторонних клиентах молчат; протокол
  открыт (BSD-3), сторонние клиенты (microlink, tailscale-rs) работают с официальным сервером открыто. Для
  личного клиента риск низкий.

7. TLS: встроенные корни Let's Encrypt, ChaCha20 первым; пин `sha256-raw` - только для стенда; без
