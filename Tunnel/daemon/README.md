# daemon

Root-демон `bbtunneld`: владеет `/dev/tunN`, ставит маршруты и DNS, следит за сменой сети, принимает команды
приложения через сокет. C-бинарь, собирается вне Momentics (WSL, gcc 9.3) и едет внутри .bar.
Решения - `../docs/DAEMON.md` (утверждён 2026-09-30, ход работы - его §16), журнал - `../docs/PLAN.md`, этап 3.

## Сборка и тесты

```
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -u root -- bash /mnt/e/dev/momentics-projects/Tunnel/daemon/build.sh [host|cross|all|live [имена...]]
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -u root -- bash /mnt/e/dev/momentics-projects/Tunnel/daemon/test/e2e/run.sh [awg] [hostroute]
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -u root -- bash /mnt/e/dev/momentics-projects/Tunnel/daemon/test/qnx/run.sh
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -u root -- bash /mnt/e/dev/momentics-projects/Tunnel/daemon/test/ts/stand_build.sh
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -u root -- bash /mnt/e/dev/momentics-projects/Tunnel/daemon/test/ts/e2e.sh [tls] [client]
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -u root -- bash /mnt/e/dev/momentics-projects/Tunnel/daemon/test/ts/saas.sh probe | KEYFILE [100.x.y.z]
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -u root -- bash /mnt/e/dev/momentics-projects/Tunnel/daemon/test/ts/direct.sh
```

`saas.sh` - демон против настоящего Tailscale: namespace `ts-saas` с выходом в интернет через NAT WSL
(на время прогона - `ip_forward` и таблица nft `bt_saas`, потом всё как было), DNS - публичный, TLS - только
встроенные корни. `probe` - выдуманный ключ: ничья сеть не затронута, сервер обязан отказать своими словами
(проверка пути: DNS, TLS, ts2021, HTTP/2, register). С файлом ключа - вход в настоящую сеть, список
устройств, ping узла по адресу; ключ идёт демону из файла (`authkey=@`), в журнал не попадает. Для такого
прогона лучше эфемерный заранее одобренный ключ с тегом - узел уйдёт из сети сам. `SAAS_NAME=<имя узла>` -
ещё и MagicDNS: узел по короткому имени (по адресу из аргумента, если он дан) и внешнее имя через пересылку.

Tailscale: `stand_build.sh` один раз собирает Go-бинарники стенда из `../../refs` (`tailscale`, `headscale`;
модули Go качаются из сети) в `build/stand/`; `e2e.sh` (около 3 минут) - демон как клиент Tailscale против
Headscale и официального `tailscaled`, журналы последнего прогона - в `build/ts-e2e*/`. Без аргументов -
этап A (plain HTTP); `tls` - этап B, TLS как в бою: control по https с тестовым CA стенда (демону -
`--ca-file`), встроенный DERP Headscale проверяется по этому CA, отдельный `derper` (регион 900) - по пину
своего самоподписанного сертификата; `client` - вместо проверок сценария код приложения и сервиса
(`client_test --tailscale`, собрать: `client/test/build.sh`). Прогонять `e2e.sh`, `e2e.sh tls` и
`e2e.sh tls client`. `stand.sh [tls] selftest` - сам стенд с двумя официальными узлами. Проверка мутациями
Tailscale: `build/ts-mut-e2e/mutate.py` (оркестратор через e2e с `BT_BIN` и `E2E_FAILFAST=1`, по одному
мутанту - у стенда постоянные имена namespace) и `build/ts-mut/run.sh` (`ts_derp`, `ts_profile`); скрипты
лежат в `build/`, не в git, как у других модулей. Демон и тесты
линкуют `libssl` (на телефоне - `libssl.a` из той же сборки OpenSSL 3.5.8, что и `libcrypto.a`).

`host` - тесты под ASan+UBSan, затем `bbtunneld` (Linux-бэкенд) и `btctl` в `build/host/`; `cross` - те же
исходники под BB10 (движок компилируется исходниками, OpenSSL статически, NEEDED только `libsocket` / `libm` /
`libc`), плюс `bbtunneld` (QNX-бэкенд) и `btctl` для телефона - оба едут в `.bar` ассетами из
`build/bb10/` (его нет в git: перед упаковкой `.bar` - `build.sh cross`); `live` - DNS-клиент против
настоящего сервера (нужна сеть).

e2e (около 2,5 минут, с `awg` - ещё минута на сборку amneziawg-go из `../../refs`): namespace `bt-phone` -
«телефон» с `wifi0` и `lte0`, демоном и настоящим tun; `bt-inet` - «интернет» с серверами WireGuard, DNS
провайдеров, DNS внутри туннеля и веб-сервером. nft в `bt-inet` режет ICMP и порт 8080 с подложки, так что
удачный ping или загрузка прошли через туннель. resolv.conf телефона - `/etc/netns/bt-phone/resolv.conf`,
его `ip netns exec` монтирует поверх `/etc/resolv.conf`; resolv.conf самого WSL не трогается. Журнал демона
последнего прогона остаётся в `build/e2e/`. `BT_BIN=<каталог>` подменяет бинарники (для проверки мутациями).
С `hostroute` всё то же идёт с `--egress hostroute` (свои сокеты мимо туннеля держат host-маршруты к
серверам, а не `SO_BINDTODEVICE`) и по дороге проверяются сами маршруты (`ip route show proto 126`);
без него - что их нет. Прогонять оба.

Зерно фаззера и любые переменные окружения передавать через файл-скрипт: Git Bash (инструмент Bash в
Claude Code) раскрывает `$var` даже внутри одинарных кавычек `bash -c '...'` ещё на стороне Windows - там он
пуст, и фаззер молча шёл с зерном 1.

## Запуск

```
bbtunneld --state DIR --socket PATH [--log FILE.txt] [--owner UID:GID] [--dns-file PATH]
          [--egress auto|fib|bind|hostroute] [--ca-file PEM] [--foreground] [--debug] [--clock-offset SECONDS]
btctl [-s SOCKET] [-t SECONDS] [-k KEY] <команда> [ключ=значение ...]      значение @ФАЙЛ - содержимое файла
btctl [-s SOCKET] [-t SECONDS] wait <профиль> <состояние>
btctl [-s SOCKET] [-t SECONDS] watch [stats]
```

`--owner` - uid:gid приложения: ему отдаются сокет и журнал, и в сокет демон пускает только root и этот uid.
На телефоне это владелец файла, который создал процесс приложения (цикл запуска берёт `data/logs/service.txt`),
а не папки `data`: ту создаёт система с другим uid. Каталога журнала нет - демон создаёт его
(один уровень: на телефоне `data/logs` песочницы) и тоже отдаёт `--owner`: туда пишет свой журнал и сервис,
а запускалка может стартовать демон раньше приложения (`docs/APP.md` §15). `--dns-file` - resolv.conf,
которым владеет Linux-бэкенд. `--egress` - как свой UDP-сокет обходит туннели. На QNX: `auto` - FIB 15, если в нём есть
маршрут по умолчанию, плюс `SO_BINDTODEVICE` на его интерфейс (хватает любого из двух); FIB 15 нет -
host-маршруты к серверам плюс `SO_BINDTODEVICE`; `fib`, `bind`, `hostroute` - только одно, чтобы на
телефоне проверить каждое без пересборки. На Linux: `bind` (он же `auto`) или `hostroute`.
`--ca-file` - корни для TLS Tailscale сверх встроенных (Let's Encrypt): `cacert.pem` из `.bar`, тестовый CA стенда.
`--clock-offset` - сдвиг часов для рукопожатий, только для теста потолка меток. Например:
`btctl -s S profile.import name=Дом conf=@home.conf`, `btctl -s S -k text log.tail lines=50`.

## Правила

- Префикс `bt_`, C gnu99, однопоточно, функции возвращают 1 при успехе (как движок).
- Демон работает от root и разбирает то, что прислал клиент: всё ограничено и отвергается, а не
  угадывается. Ключ протокола - 1-32 символа `[a-z0-9_.]`, блок - до 256 КБ и 256 строк; id профиля - ровно
  8 hex-символов, проверяется при каждом обращении (он становится частью пути).
- Разбор на месте (`bt_block_parse`, `bt_meta_parse`) пишет NUL в `text[len]`: буфер должен иметь этот байт.
- Профиль существует, пока есть его `.meta`. Запись: `.conf`, потом `.meta`; удаление: `.meta`, потом `.conf`.
  После падения `bt_store_sweep` убирает `*.tmp` и `.conf` без `.meta`.
- В журнал никогда не попадают приватный ключ, PSK и `HeaderProtectionKey`. Буфер `.conf` отдавать
  `bt_store_free_conf` - он затирается.
- DNS-клиент спрашивает A и AAAA, IPv4 предпочтительнее: пришли адреса A - поиск окончен, AAAA не ждём.
  SERVFAIL / REFUSED - сразу следующий сервер; NXDOMAIN - сразу отказ. 4 раунда по 2 с.
- Резолвер WSL (`10.255.255.254`) иногда молчит на первый запрос и отвечает на повтор, а имена под
  `example.com` дают пустой ответ вместо NXDOMAIN - это сервер, не мы (проверено сырым запросом).
- Ответ команды собирается в одном статическом буфере, событие - в другом. Команда может вызвать
  событие посреди своего ответа (`tunnel.down` шлёт `event=tunnel`); на общем буфере событие затирало
  ответ, и клиент не получал его вовсе - e2e поймал это с первого прогона.
- Смена сети: события netlink / inotify копятся 500 мс, потом одна обработка. Сокеты туннеля
  пересоздаются, только если сменился интерфейс маршрута по умолчанию; тогда же имена серверов
  разрешаются заново и сразу идёт рукопожатие. Маршруты и DNS переставляются на каждом событии
  (идемпотентно: существующий маршрут - не ошибка, свой resolv.conf - не событие).
- Свой resolv.conf пишется на месте, не переименованием: цель bind-mount заменить нельзя. «Система» -
  всё, что пишет в него кто-то другой, в том числе ровно прежний текст поверх нашего.
- QNX-бэкенд (`bt_plat_qnx.c`), то, что в коде не очевидно:
  - `SO_BINDTODEVICE` на QNX принимает `struct ifreq`, а не голое имя, как Linux.
  - Удаление маршрута сначала спрашивает `RTM_GET` точно этот префикс и удаляет, только если он идёт через
    наш tun: иначе `AllowedIPs = 192.168.1.0/24` при такой же домашней сети (добавление ответило
    `EEXIST` - «уже есть») при опускании стёр бы маршрут локальной сети.
  - Всякий routing-сокет слышит всё, что делают другие: перед запросом он вычищается, ответ `RTM_GET`
    ищется по pid и seq. Наблюдатель пропускает своё: маршруты с нашим pid и адреса, ссылки, анонсы на tun.
  - У `confstr(_CS_RESOLVE)` нет уведомлений, а сетевой менеджер может переписать его позже события
    PPS: пока наш DNS стоит, демон заглядывает туда раз в 5 с (`bt_net_deadline` / `bt_net_check`, на
    Linux - пустые). Записанное сравнивается с тем, как оно читается обратно.
  - **Резолвер BB10 10.3 `_CS_RESOLVE` не читает** (2026-10-16, PLAN §0): в `libsocket.so.3` этого имени нет,
    серверы и домены идут из PPS `/pps/services/networking/status_public` (`nameservers`, `searchdomains`), а
    их ставит системный `net_pps` по `priority` интерфейсов. `_CS_RESOLVE` он сам заполняет из них для старых
    программ. DNS туннеля через `_CS_RESOLVE` на телефоне не действует.
  - **Поэтому DNS туннеля - два атрибута `status_public`** (демон 0.1.6; опыт на телефоне: `ping nas`
    сразу разрешился через MagicDNS). Запись - дописыванием (`O_APPEND`), одной `write`: `O_TRUNC` опустошил бы
    весь объект `net_pps`. Наша запись, прочитанная обратно (`status_public?wait`), серверами сети не
    считается - их значения хранятся отдельно (`pps_ns`, `pps_search`) и при опускании пишутся назад.
    `net_pps` переписал наши - ставим свои снова; больше 10 раз за минуту - оставляем объект ему (строка в
    журнале). Одинаковое не пишется повторно: каждая запись будит всех читателей объекта. Журнал после
    падения хранит `|net:...|search:...|ours:...`: при старте значения сети возвращаются, только если в
    объекте всё ещё наши. Проверка без телефона - `test/qnx/run.sh` (раздел DNS вынимается из
    `bt_plat_qnx.c` как есть и собирается с заглушками).
  - `msg::net_connected` в `/pps/services/networking/control` для нашего tun (опыт 2026-10-16, с разрешения
    Миши): `net_pps` отвечает без ошибки и ставит `nameservers` и `searchdomains` в `interfaces/tun1`, но
    `status_public` не меняет (tun нет в его `priority`, шлюза нет) - системный DNS прежний. И перенастраивает
    интерфейс по сообщению: без `ip4_address` в нём IPv4 `100.x` на tun заменён на `0.0.0.0`, и
    `net_disconnected` его не вернул (лечится переподъёмом туннеля). Без полного ip_config не слать никогда.
    Телефонный шелл (PD KSH): нет `printf` и `head`; `print -r --` - встроенный.
  - DNS в `_CS_RESOLVE` пишется как у системы (`nameserver_A_nameserver_B`), домены - `_search_a_b`: в
    строке не может быть ни одного пробела, `confstr(_CS_SET | _CS_RESOLVE)` отвечает `EINVAL` (телефон,
    2026-10-16, сборка 21: `_search tailb78ad.ts.net` - MagicDNS не встал; страница resolv.conf QNX: «can't
    include spaces; separate the keywords by underscores»). У WARP доменов поиска не было, и до MagicDNS
    это место на телефоне не исполнялось. Отказ с доменами - `dns_apply_servers` ставит серверы без них.
  - tun после закрытия уничтожается (`SIOCIFDESTROY`) - уходят его адреса и маршруты; при открытии со
    старого устройства снимаются адреса (след падения без журнала).
  - IPv6-адрес: `IN6_IFF_NODAD` io-pkt (KAME времён NetBSD 5) считает флагом «только для чтения» и отвечает
    `EINVAL` (Passport 2026-10-15: с ним - `Invalid argument`, без него - ok). Адрес ставится без `NODAD` и
    около секунды проходит DAD; Linux свой `IFA_F_NODAD` принимает.
  - `/dev/tun0` с загрузки держит системный `base/bin/TunnelManager`: `Resource busy`, интерфейса `tun0`
    нет. Наши туннели начинаются с `tun1` - это норма, не утечка юнита.
  - `Colls` у tun в `netstat -in` - не коллизии, а выброшенные пакеты (так считает драйвер NetBSD tun): в
    `tun_output` - очередь отправки tun полна, демон не успел забрать (то же число - `Drops` в
    `netstat -in -d`); в `tunwrite` - полна очередь IP-входа (`sysctl net.inet.ip.ifq.drops`), `writev`
    отвечает `ENOBUFS`. На телефоне было первое: 111 у Tailscale, при нагрузке (до 1 600 пакетов/с) - 0,
    то есть всплеск. Очередь tun - 256 пакетов, и `read_tun` берёт до 256 за виток (`TUN_BURST`, демон
    0.1.7; было 64).
  - Маршрут запоминает адрес интерфейса, который нашёл, когда ставился (`route get` - `local addr`).
    Маршрут на tun, поставленный раньше IPv4-адреса, остаётся с `local addr: tun1`: TCP не находит
    исходящего адреса, `connect()` сразу отвечает «сеть недоступна» и ничего не шлёт, а ping (raw) идёт.
    Так было у Tailscale (2026-10-16, браузер телефона к NAS): маршруты ставились до адресов netmap.
    Теперь после, а первый адрес семейства переставляет маршруты этого семейства (`ts_routes_rebind`).
- Tailscale, путь к узлу через ретрансляторы (`bt_ts_send_peer`, как magicsock): его домашний, если открыт;
  иначе тот, через который он говорил последним, - только 30 с после его пакета (`VIA_FRESH_NS`); иначе
  соединиться с его домашним. Узел закрывает чужой ретранслятор через минуту после последней записи, а
  ретранслятор из нескольких серверов может не прислать PeerGone: без срока пакеты шли туда в пустоту
  (телефон, 2026-10-16: SYN браузера к NAS через ретранслятор 4 восемь минут спустя). Проверка -
  `SAAS_QUIET=200 test/ts/saas.sh KEY 100.x` (ping, 200 с тишины, ping).
- Цикл запуска на телефоне (`boot/bbtunneld-boot.sh`):
  - `cksum` QNX выравнивает CRC по ширине 10 (`  22166864    2845296 путь`): `.cksum` читается через
    `IFS= read -r`, обычный `read` срезал пробелы, и при CRC короче 10 цифр демон копировался заново перед
    каждым стартом.
  - Копия демона, сделанная после загрузки, не запускается (`Operation not permitted`), а лежавшая в RUN
    при загрузке - запускается (2026-10-15, четыре раза подряд). Новый демон на телефоне - только после
    перезагрузки; как это даёт root-настройка, решает её владелец. Поэтому цикл кладёт копию нового пакета
    сразу, при работающем демоне, и помечает её `RUN/copied-this-boot`: неудачный старт такой копии пишет в
    журнал, что она запустится после перезагрузки. Приложение старый демон не перезапускает (APP §9).
- Host-маршруты к серверам (`--egress hostroute`; на QNX ещё `auto` без FIB 15), DAEMON.md §5:
  - Какие адреса - решает ядро: конечные точки пиров и DNS-серверы, пока ищется имя, из них - те, что
    ловят маршруты туннелей (`wg_allowedips_lookup`). Бэкенд только ставит и убирает (`bt_bypass_set`).
  - Маршрут встаёт раньше пакета: явный пересчёт перед рукопожатием (подъём, найденное имя, смена сети)
    и страховка в `up_send` / `lookup_send` - адрес не из набора (пир переехал) пересчитывает набор до
    `sendto`. Проверено мутациями: без явных пересчётов одна страховка держит весь e2e, без страховок
    и пересчётов e2e падает.
  - Свои помечены: QNX - `RTF_PROTO2` (+ `RTF_STATIC`), Linux - `proto 126`. Удаление на Linux называет
    протокол - ядро не отдаст чужой; на QNX сначала `RTM_GET` и проверка метки. Чужой host-маршрут к тому
    же адресу (`EEXIST`) остаётся как есть и не удаляется.
  - Адрес в подсети интерфейса (DNS домашнего роутера) маршрута не получает: его уводит маршрут подсети.
  - После события сети каждый свой маршрут переставляется, если шлюз сменился, и ставится снова, если
    его стёрли (на Linux `ip link set down` стирает маршруты через интерфейс сам).
- e2e: фоновый запуск shell-функции - подоболочка, `$!` - её PID, а не демона; `kill` промахивался, и
  демоны копились, деля сокет и журнал. Демон запускается прямо `ip netns exec ... &` (он делает exec на
  месте). С тех пор второй демон на тот же каталог состояния и не стартует (блокировка `state/lock`).
  С DNS-заглушками и веб-сервером было то же самое, только до шага 3 никто не заметил: они переживали
  каждый прогон (в WSL их копились десятки) и держали его вывод - конвейер `run.sh | grep` не кончался.
  Теперь и они идут прямо через `ip netns exec` (`bg_inin`), с выводом в `/dev/null`.
- `BT_VERSION` поднят - пересобрать `client_test` (`client/test/build.sh`): он берёт версию из того же
  `bt_version.h` при сборке, и старый бинарник валит `run.sh client` на «the daemon is this build's» (APP §9).
- Уборка стенда руками: `pkill -f <шаблон>` внутри `bash -c "..."` убивает и сам этот `bash` - шаблон есть в его
  же командной строке. Скрипт-файлом, `pgrep -f` и пропуск `$$`.
- e2e: `ip route show | grep -q` под `pipefail` - гонка: `ip` пишет маршрут за маршрутом, `grep -q`
  выходит на первом совпадении, следующая запись `ip` получает SIGPIPE, и проверка ложна при
  маршрутах на месте. Вывод сначала целиком в переменную, потом `grep <<<`.
- Linux-бэкенд до шага 3 считал сменой сети и то, что делал сам (tun, его адреса, свои маршруты): через
  500 мс после подъёма демон устраивал себе «смену сети» с полной перепроверкой, и она чинила что
  угодно - проверка мутациями показала, что e2e не видел даже полного отсутствия пересчётов перед
  рукопожатием. QNX-бэкенд своё отбрасывает (pid, tun), на телефоне этой подпорки нет. Теперь и Linux
  отбрасывает: сообщения с port id своего единственного сокета запросов и сообщения ядра о tun.
- «Сообщение о tun» - по имени, пока устройство живо, а когда его уже нет - по запомненным индексам
  своих устройств (последние 8). Удаление маршрутов и адресов уничтоженного tun приходит, когда имени по
  индексу уже не найти: без этого каждый `tunnel.down` давал «смену сети» через 500 мс, и она снова
  чинила всё за ядро, если следом шёл `tunnel.up` (так выжила мутация «ни страховок, ни пересчётов»).
  На QNX то же. Индекс живого чужого интерфейса решается по его имени - переиспользованный индекс за
  наш не сойдёт. Какое сообщение засчитано сменой сети - строка `network: message ...` при `--debug`.

### Tailscale (TAILSCALE.md)

- Сервер Go после 101 на `/ts2021` не шлёт кадра ошибки - отказ рукопожатия выглядит как закрытие
  соединения в состоянии SENT. Ключ сервера из кэша профиля тогда выбрасывается: следующий раз - снова
  `GET /key`. Ответ на рукопожатие и первые записи сервер шлёт одним куском: остаток после заголовков 101
  сразу идёт в `ts_noise_receive`, в том же проходе.
- Большие структуры - только в куче: `ts_h2` ~140 КБ, `ts_derp` ~64 КБ (буфер кадра), `ts_http1_resp`
  ~9 КБ.
- Колбэк наверх из `bt_tsc` или `bt_relays` может уронить соединение, внутри которого он вызван: сброс
  внутри колбэка только помечается и выполняется, когда колбэк вернулся (`in_upcall`, счётчик `gen` у
  control; флаг `busy` у соединения DERP, его не вытесняют и не роняют изнутри). Иначе освобождённые
  `ts_h2` / `ts_derp` читались бы дальше.
- Соединение, созданное посреди разбора одного `poll`, может получить номер fd только что закрытого -
  и чужие `revents`. Такие события пропускаются: `bt_tls_step` зовётся только для fd, ушедшего в этот
  `poll` (`in_poll`).
- Состояние туннеля Tailscale туннель спрашивает сам на каждом витке (`bt_ts_state`); из `bt_ts` вызова
  наверх нет - остановленный вход освобождает `bt_ts`, и это нельзя делать изнутри него.
- Профиль, который пишет работающий туннель (кэши, регистрация), сначала перечитывается: если node key на
  диске уже другой (`profile.update authkey=` во время работы), туннель ничего не пишет - иначе затёр бы
  новый вход.
- Транспорт Tailscale идёт по маршрутам, и пересоединяется он только при смене интерфейса выхода (и при
  подъёме или падении полного туннеля), а не на каждое событие сети: ядро досылает адрес link-local
  после DAD через секунду-другую после подъёма интерфейса, и e2e ловил лишнее переподключение.
- Стенд: `tailscaled`, чей namespace уже удалён, не завершается по SIGTERM - `wait` в уборке висел
  вечно (e2e печатал «all passed» и не выходил). `stand_down` гасит процессы до удаления namespace, через
  3 с - KILL.
- Стенд, Headscale 0.29.4: после `nodes expire` и повторной регистрации узла с новым ключом пиры получают
  новый ключ, но не снятое истечение - у них остаётся старый `KeyExpiry`, и они отбрасывают узел до своего
  нового map-потока. Официальный сервер так не делает; `test/ts/e2e.sh` перезапрашивает map у NAS.
- Узел, удалённый из tailnet (админом в консоли или временный - ключ Ephemeral - через 30-60 минут
  офлайн), официальный сервер на map отвечает «HTTP 404 node not found», а не 401/403. До 0.1.9 демон
  на это переподключался каждые 2-16 с, приложение писало «нет связи с Tailscale» (телефон, 2026-10-22).
  Теперь на любой отказ карты (4xx, кроме 429) демон спрашивает control, как Go-клиент при каждом старте
  (`cc.Login` в ipnlocal): register с одним ключом узла, без ключа авторизации (`check_login`). Просит
  вход заново (AuthURL) или 404 - узла нет, причина `removed`; NodeKeyExpired - `expired`; узел на месте -
  map снова после растущей паузы. Проверено на официальном сервере (`saas.sh` с `SAAS_REMOVE`, узел
  удалён в консоли, 2026-10-22): сервер закрыл поток карты, новый map отклонён, проверка ответила
  `authURL=1, machineAuthorized=0` - `removed` через секунду. Headscale 0.29.4 так не делает: поток
  обрывает, а следующий map отдаёт с нашим узлом истёкшим - на стенде удаление читается как `expired`
  (`e2e.sh`, раздел 6b), проверочный запрос там не нужен.
- Новый вход (`profile.update authkey=`) может дать новый узел с другими адресами. Старые из кэша профиля
  вставали на tun первыми, и маршрут tailnet брал источником старый адрес - узлы такие пакеты отбрасывают
  (телефон, 2026-10-22: `route get` к NAS - local addr 100.117.117.116 при новом 100.114.0.124).
  `ts_profile_relogin` кэш адресов стирает: адреса приходят с netmap через миг после входа.
- STUN (этап 2): датаграмма с «cookie» `21 12 a4 42` в байтах 4-8 - не обязательно STUN: у пакета
  WireGuard там индекс получателя. Поэтому как STUN разбирается только датаграмма от сервера текущего
  раунда (`ts_stun_knows`), остальное идёт дальше, как раньше.
- Стенд, `direct.sh`: официальный `tailscaled` выбирает домом регион, который быстрее ответил на STUN,
  даже если в нём только STUN-узел (netcheck не спрашивает, есть ли там DERP), - и остаётся без
  ретранслятора. В настоящей карте таких регионов нет; второй STUN-сервер стенда (`stun_stub.py`,
  регион 998) отвечает с задержкой 50 мс.
- Стенд, пробой NAT: роутер без фильтра на входе ломает его - и официальному клиенту. Наш первый ping
  приходит на домашний роутер раньше, чем NAS что-то послал, роутер принимает его как соединение к себе,
  conntrack держит запись (наши пинги её продлевают), и NAT отдаёт исходящему пакету NAS другой порт.
  Голая проверка двух NAT (2026-10-22): без фильтра - 0 пакетов в обе стороны, с `iifname <uplink> ct
  state new drop` на входе - по 49 000 за 6 с. Роутеры стенда с фильтром, как домашние.
- Адрес, которого у узла больше нет (админ дал другой, новый вход), снимается с tun (`bt_if_addr_del`:
  netlink `RTM_DELADDR` / `SIOCDIFADDR(_IN6)`), когда на его месте уже адрес того же семейства, и маршруты
  семейства переставляются на оставшийся. Список без адресов семейства ничего не снимает.
- IPv6 в прямых путях: свои адреса - только глобальные (2000::/3), не ULA: официальный клиент ULA не
  объявляет, пока есть что-то ещё, и на стенде ULA-адреса NAS просто не появились бы - у домашней сети
  стенда `2001:db8:77::/64`. STUN по IPv6 - только при своём глобальном IPv6. Ошибки отправки IPv6 - в своём
  буфере (`udp6_problem`): общий с IPv4 сбрасывался бы каждой удачной IPv4-отправкой, и строка «no route»
  повторялась бы раз в раунд.
- Раздельный DNS: сервер управления (и Headscale) в `DNSConfig.Routes` сам шлёт 65 маршрутов - обратные
  зоны tailnet (`64..127.100.in-addr.arpa`, `0.e.1.a.c.5.1.1.a.7.d.f.ip6.arpa`) без серверов. Предел в 16
  маршрутов заполнялся ими, и маршрут самой сети отбрасывался - имя уходило к резолверу сети (стенд,
  2026-10-22). Предел 128; в журнале такие маршруты только считаются («65 MagicDNS's own»).
- Стенд: проверка TCP одной попыткой с `nc -q 1` падала примерно раз в три прогона этапа B - сразу после
  переезда NAS в другой регион DERP «ping» одной стороны приходил, когда слушатель другой уже ушёл (он
  закрывается через секунду после своей части). `-q 3`, тайм-аут 8 с, шаг - `within 30`, как у пингов; в
  `direct.sh` помощник ещё и ждёт своего слушателя, чтобы повтор нашёл порт свободным.
- `test_tls` один раз упал «certificate is not yet valid» (2026-10-22) и прошёл при повторе: PKI делается
  при каждом запуске с началом действия «сейчас», а WSL при синхронизации часов иногда сдвигает их назад.
  Сбой обвязки, не кода; повторить.
- Ключ Ephemeral делает узел временным: для `saas.sh` удобно (узел уходит сам), для телефона нельзя.
  Истёкший или отозванный ключ авторизации уже вошедшим устройствам не вредит (Tailscale KB 1085).
- Путь пакета к узлу - как у magicsock: есть соединение с домашним регионом узла - через него; нет, но
  его пакеты пришли к нам через другой регион - обратно тем же путём; иначе - новое соединение с его
  домом. Поэтому в чужой регион телефон идёт, только если заговорил первым: узел, который писал нам
  через наш дом, мы так и не увидим в его регионе. e2e этапа B переводит NAS в регион, который не наш
  дом, до первого пакета - иначе одна из двух проверок сертификата (CA или пин) просто не запускается.
- Домашний регион нельзя мерить временем TCP connect: посредник на пути (VPN на ПК - ExpressVPN у
  Миши, прокси оператора) сам отвечает на connect к любому адресу, и все регионы выходят одинаковыми
  (по 21 мс; домом стал Нью-Йорк при NAS во Франкфурте). Мерим TLS-рукопожатие от конца connect до
  конца рукопожатия - круг до самого сервера (`bt_ts_relay.c`, `probe_check`); `saas.sh` печатает мс по
  регионам.
- Стенд, этап B:
  - `derper --certmode manual --hostname <IP>` без сертификата в `--certdir` делает самоподписанный и
    печатает готовый узел карты с `CertName: sha256-raw:<hex>` - SHA-256 всего DER, как
    `openssl x509 -outform DER | sha256sum`;
  - карта DERP для `derp.paths` Headscale читается yaml.v3 - поля строчными: `certname`, `derpport`;
  - `tailscaled` берёт тестовый CA из `SSL_CERT_FILE`;
  - узел переводится в другой регион `tailscale debug force-prefer-derp <id>` и `debug restun`, но только в
    тот, что замерен: регион с `Avoid` (у нас и в netcheck) не замеряется, туда не перевести.
- MagicDNS (TAILSCALE.md §8a):
  - Системный DNS - `100.100.100.100`, а за ним серверы, что были бы без MagicDNS (DNS= полного туннеля или
    сети): демон упал - tun и маршрут `100.64/10` ушли, резолвер телефона после таймаута на первом идёт ко
    второму; журнал при старте возвращает системный. Без второго телефон остался бы без имён до старта демона.
  - Хук `resolvers` (имена control и DERP, пересылка наверх) - никогда не `100.100.100.100` (`dns_base` берёт
    DNS= туннеля или `bt_dns_system`, а он - всегда серверы сети): иначе запрос ходил бы по кругу.
  - Выключение - в тот же проход: `stop()` (вход истёк, отказ) -> `dns_refresh` -> хук `dns_changed` ->
    `dns_reconcile`. Освобождение `bt_ts_stop` хуков не зовёт: туннель сам зовёт `dns_reconcile` после
    `release`.
  - `dns_fd` после `calloc` - сразу `-1`: ноль - это stdin, и `bt_ts_stop` закрыл бы его.
  - Поиск в `_CS_RESOLVE` - целыми словами, не больше 6 и 255 символов (что читает резолвер): обрезанное слово
    стало бы доменом, которого нет.
  - Стенд: Headscale с `magic_dns: true` требует `base_domain`; `Proxied` = `magic_dns`, `base_domain` идёт
    первым в `Domains`, узлы - `<имя>.<base_domain>.`. В тестах имя - через `getent ahostsv4`: `getent hosts`
    берёт IPv6, если он есть.
- Прямые пути (TAILSCALE.md §11a):
  - Узел переходит на прямой путь к нам только по нашему pong на его ping - наш WireGuard по UDP его путь не
    меняет (magicsock). Поэтому каждый ping от узла из netmap получает pong туда же, откуда пришёл.
  - Свой адрес узел узнаёт из `Endpoints` в коротком map-запросе (`OmitPeers`): в потоковом сервер их не
    читает (capver ≥ 68).
  - Пинги и CallMeMaybe - из `bt_ts_send_peer` (трафик к узлу и есть повод искать путь) и из таймера
    (heartbeat 3 с, пока сессия активна 45 с). Без трафика - тишина, батарея как была.
  - `ts_path_next` после конца сессии не должен возвращать прошедший срок heartbeat - иначе цикл демона
    крутится вхолостую; `ts_path_tick` гасит сессию при первом же вызове после неё.
  - Стенд: `TS_DEBUG_ALWAYS_USE_DERP` превращает UDP-сокет `tailscaled` в «вечно блокирующий» - ни STUN, ни
    disco; для `direct.sh` NAS запускается без него. В WSL `nft` не фильтрует семейство `bridge`
    («Operation not supported»): LAN-путь закрывается правилами в namespace телефона. `fwd` - ключевое
    слово `nft`, цепочку так не назвать.
- `within N` в `test/ts/*.sh` ждёт по часам (`$SECONDS`): прежний счёт попыток (N x 5) при ping с `-W 2`
  растягивал провал «within 20» до 220 с - проверка мутациями шла часами. В `test/e2e/run.sh`
  (WireGuard) `within` пока считает попытки: зелёные прогоны это не задевает, провалы - дольше.
- Скрипт bash нельзя править, пока он идёт: bash читает его по ходу, и правка посреди прогона
  исполняется со сдвигом. Прогоны e2e и проверку мутациями - сначала остановить.
- Тест TLS (`test/tls`): `openssl s_server -quiet` по умолчанию не замечает конца stdin, а с
  `-no_ign_eof` конец stdin - это close_notify (без `-quiet` соединение рвётся без него); `openssl req` не
  пишет CN длиннее 64 символов, а у мета-сертификата derper 71 - такие только читаются; у листов Let's
  Encrypt CN больше нет, имя - только в SAN.
- Векторы на Go: Go 1.27 включает `GOEXPERIMENT=jsonv2` - `encoding/json` читает иначе, чем у Tailscale
  1.102.5 (Go 1.26); генератор netmap собирается с `GOEXPERIMENT=nojsonv2`. В Go 1.27 `x/net/http2` стал
  обёрткой над `net/http`, и `Shutdown` h2c-сервера не шлёт GOAWAY (тест берёт
  `http.Server.Protocols.SetUnencryptedHTTP2` или `-tags http2legacy`).
- Скрипты-заплатки и векторы с `\n`, `\uXXXX` писать файлами, не heredoc из Git Bash: обратные слэши там
  теряются (так тихо перестали проверяться экранирования в пробах Go).
